# Wire protocol — PearCircle v1

**Status**: Approved 2026-05-03. All open questions resolved (see `DECISIONS.md`); approval record in `reviews/2026-05-03-wire-protocol.md`. Subsequent protocol changes follow the Constitution §3 proposal gate.

**Amendments**:
- 2026-05-04 — invite link grammar (§2) gains a required `bootstrap=<hex(32)>` field carrying the per-circle Autobase bootstrap-writer-core public key. See `DECISIONS.md` 2026-05-04 and `reviews/2026-05-04-invite-bootstrap-amendment.md`. v1 remains the floor; no shipped peers existed at amendment time.

**Goal**: Define the wire protocol for PearCircle v1 (invite link, Hyperbee schema, Autobase apply branches, location-update message envelope, geofence transition format) so cross-peer interop is stable from the first device build.

**Tier**: T3. New protocol from scratch. Old peers do not exist yet, so the only "compat" obligation is forward-compat for the v1 series we choose to ship.

## Scope

In scope:
- Invite link format and the field grammar for each query param
- Hyperbee key schema for local-only data and for Autobase-replicated data
- Autobase apply branches per record kind
- The signed envelope format for location updates and geofence transitions
- Hyperswarm topic derivation per circle
- Dedup and freshness windows for location updates

Out of scope:
- Trip recording (v2)
- SOS messaging (v2)
- Identity migration across devices (deliberately omitted, see DECISIONS 2026-05-03)
- Driving safety (v2+)

## Compat

No prior peers exist. v1 is the floor. We MUST tag every replicated record with a `v: 1` field so that future v2 peers can detect and either translate or refuse. Strict additive evolution within v1: new optional fields are free; new required fields bump the version.

## Design

### 1. Identity

- 32-byte Ed25519 keypair generated by `sodium-universal` on first launch
- Stored only in local Hyperbee under `identity` (never replicated)
- Public key is the canonical identifier of a device throughout the system
- Lost devices are not recoverable; user obtains a new invite (DECISIONS 2026-05-03)

### 2. Invite link

```
https://peerloomllc.com/circle/join?circle={base64url(circleId)}&name={name}&key={hex(circleKey)}&bootstrap={hex(autobaseBootstrap)}&inviter={hex(pubkey)}
```

- `circleId` is a 32-byte random value, stable for the life of the circle
- `circleKey` is the Hyperswarm topic seed (32 bytes hex, 64 chars)
- `name` is the display name of the circle, ≤ 64 chars, URL-encoded
- `bootstrap` is the public key of the per-circle Autobase's bootstrap writer core (32 bytes hex, 64 chars). Joiners pass this to `new Autobase(store, bootstrap, ...)` to anchor the replicated view. Distinct from `inviter` because the inviter need not be the original owner (any-member-can-invite, DECISIONS 2026-05-03).
- `inviter` is the issuing member's public key, ≤ 64 hex chars

Legacy custom-scheme accepted: `pear://pearcircle/join?circle=...&name=...&key=...&bootstrap=...&inviter=...`

Per-app `/circle/` path prefix avoids host collision with PearCal's `/join` on `peerloomllc.com`.

### 3. Hyperbee keys

**Local-only (never replicated):**

| Key | Value |
|-----|-------|
| `identity` | `{ publicKey: hex, secretKey: hex, createdAt: number }` |
| `profile:local` | `{ displayName: string, avatarBlobId?: string, updatedAt: number }` |
| `geofence:registered:{circleId}:{placeId}` | `{ registeredAt: number }` (mirror of OS state) |
| `trips:{ts}` | `{ start, end, polyline, distance }` (opt-in, not shared by default in v1) |

**Replicated (Autobase view per circle):**

| Key | Value |
|-----|-------|
| `circle` | `{ id, name, ownerKey, createdAt, v: 1 }` |
| `member:{pubkey}` | `{ pubkey, displayName, avatar?: base64jpeg, joinedAt, v: 1 }` (avatar ≤ ~30KB encoded, client-side downscaled to ~96x96) |
| `place:{id}` | `{ id, name, lat, lon, radiusMeters, createdBy, createdAt, v: 1 }` |
| `lastSeen:{pubkey}` | `{ pubkey, lat, lon, accuracy, ts, battery?, isMoving?, v: 1 }` |
| `transition:{ts}:{pubkey}` | `{ pubkey, placeId, kind: 'enter'|'exit', ts, v: 1 }` |
| `removed:{pubkey}` | `{ pubkey, removedBy, ts, v: 1 }` (tombstone for kicked members) |
| `presence:{pubkey}` | `{ pubkey, state: 'visible' | 'muted', setAt, expiresAt?, v: 1 }` |

`lastSeen:{pubkey}` is single-row-per-member. Apply branch overwrites if incoming `ts > existing.ts`. Older records dropped silently.

`transition:{ts}:{pubkey}` is append-only. Pruned by client after a configurable retention window (default 30 days) using a local sweep, NOT a replicated `del` op.

### 4. Autobase apply branches

One apply branch per record kind. Each writes to the linearized view as above. Conflict policy:
- `circle`: owner-write only; non-owner appends ignored
- `member`: any current writer can append; new entries also drive Autobase `addWriter` for the new pubkey
- `place`: any current member; last-write-wins on `id` collision by `createdAt`
- `lastSeen`: any current member writing for their own pubkey ONLY; cross-member writes ignored
- `transition`: any current member writing for their own pubkey ONLY
- `removed`: owner-write only; sets a tombstone that suppresses future appends from `pubkey`
- `presence`: any current member writing for their own pubkey ONLY; cross-member writes ignored. While `state === 'muted'`, the writing client suspends new `lastSeen` and `transition:` appends until `expiresAt` passes or the user toggles back to `visible`

### 5. Location-update envelope

All `lastSeen` and `transition` records are signed by the appending member. Verification key is the writer's pubkey, which Autobase already binds to the writing core.

Unsigned envelope (canonicalized JSON) MUST contain:
- `pubkey` (must equal the writing core's identity)
- `ts` (monotonic, UTC ms since epoch; reject anything > 5 min in the future per local clock)

Updates are deduped by `(pubkey, ts)` and rate-limited at the writer to one per 30 s in foreground, one per 5 min from significant-change-location, plus geofence transitions which are not rate-limited.

### 6. Hyperswarm topic

Topic = `blake2b(circleKey)` (32 bytes). One topic per circle. No global discovery topic.

### 7. Geofence transitions

Each `place` record creates a corresponding OS-level region monitor on every member device. iOS caps at 20 regions per app — when exceeded, the client registers the 20 places nearest the user's `lastSeen` and re-evaluates on significant location change. Android cap is 100; v1 will not hit this in practice.

A geofence enter/exit fires the native callback, which calls into the worklet via `geofence:transition`. The worklet appends a `transition:{ts}:{pubkey}` record AND updates `lastSeen:{pubkey}` in one Autobase append.

## Verify

- jest unit tests for `buildInvite` / `parseInvite` round-trip and rejection cases
- jest unit tests for the canonicalize+sign+verify path
- Two-device manual smoke: pair, share location, define a Place, walk through it, both devices observe enter then exit
- Background smoke: kill app on device A, walk through Place, device B observes the transition (within 1-2 minutes)

## Rollback

The protocol is unshipped, so rollback before the first public build is a code revert. Once shipped, breaking changes require a major-version bump (`v: 2`) and per-record translation logic in the apply branches.

## Open questions

1. ~~**Tile host.**~~ Resolved 2026-05-03: Protomaps hosted API for v1, self-hosted PMTiles on Cloudflare R2 if we cross the 1M-request soft cap. Tile-source URL kept remotely configurable so the swap is config-only. See `DECISIONS.md`.
2. ~~**Retention window for `transition:` records.**~~ Resolved 2026-05-03: 30 days, fixed in v1, applied as a local sweep (no replicated `del`). User-configurable later via an additive `transitionRetentionDays` field on the `circle` record. See `DECISIONS.md`.
3. ~~**Battery and isMoving fields.**~~ Resolved 2026-05-03: both ship in v1. Battery is free (no permission). `isMoving` requires `NSMotionUsageDescription` (iOS) and `ACTIVITY_RECOGNITION` (Android), both prompted in onboarding. Output smoothed before flipping. See `DECISIONS.md`.
4. ~~**Per-member visibility controls.**~~ Resolved 2026-05-03: separate `presence:{pubkey}` row with optional `expiresAt`. When muted, writer suspends `lastSeen` and `transition:` writes; renderer hides location entirely (no stale pin). Forward-only privacy; past data not redacted in v1. See `DECISIONS.md`.
5. ~~**Circle admin model.**~~ Resolved 2026-05-03: any current member can invite (any writer may `addWriter`); only owner (`ownerKey`) can append `removed:{pubkey}` tombstones. A future `inviteMode` field on `circle` can tighten this additively in v2 if needed. See `DECISIONS.md`.
6. ~~**Avatar blob storage.**~~ Resolved 2026-05-03: inline base64 JPEG on `member:{pubkey}`, downscaled to ~96x96 client-side, ~30KB cap. Migrate to Hyperdrive in v2 only when other binary media (place photos, voice notes) justifies the extra primitive. See `DECISIONS.md`.
