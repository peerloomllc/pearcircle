# REVIEW — `member:{pubkey}.avatar` widens to data URL with dual byte budget

**Date**: 2026-05-05
**Tier**: T3
**Proposal**: `proposals/2026-05-03-wire-protocol.md` (amended)
**Decision**: `DECISIONS.md` 2026-05-05 — avatar widens to data URL; static cap ~42KB, animated cap ~500KB

Wire-protocol v1 §3 amended to widen `member:{pubkey}.avatar` from a raw base64 JPEG string to a full data URL of any image mime type (`data:image/jpeg;base64,...`, `data:image/gif;base64,...`, etc), so animated GIFs and animated WebP render correctly without canvas re-encoding flattening them to a single frame. Two byte budgets apply, matching PearGuard's pattern: static formats (JPEG/PNG) keep the original ~42KB base64 cap with client-side downscaling to 96×96; animated formats (`image/gif`, `image/webp`) stored as-is up to a ~500KB base64 cap. Bare enforces the larger ceiling; UI applies per-format strictness so static-format avatars stay replication-cheap. Renderer treats strings missing the `data:` prefix as legacy raw-base64 JPEG, so existing avatars from earlier v1 builds keep rendering. v1 remains the floor — no peers shipped beyond the two test devices, so this is an in-flight amendment, not a v1→v2 transition. Affects `src/bare.js` (cap raised to 500_000, profile:set extracts the base64 portion before checking length, accepts data URLs and legacy raw base64), `src/ui/App.jsx` (`avatarSrc` helper normalizes both shapes for the three render sites — Avatar component, ProfileView preview, marker pin renderBubble; `onPickFile` does mime-aware raw-vs-compress routing). Cross-device smoke 2026-05-05: D1 saved an animated WebP avatar; D2 saw it animate in the bottom-sheet roster and on the map marker. Old member rows from earlier in the session still render as static JPEGs via the legacy path. Signed off by Tim.
