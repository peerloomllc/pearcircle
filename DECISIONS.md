## 2026-05-19 — global seeder setup: one bundle mint for all circles, top-level Seeders UI
Tier: T2
Context: The blind-seeder feature (proposal 2026-05-19) shipped seeder management per-circle — a member minted a `/circle/seed` invite one circle at a time via a Broadcast icon on each circle row in Settings → Circles, and the desktop seeder enrolled one invite per call. The desktop-launcher Phase 4 e2e smoke surfaced that this doesn't match real usage: someone running a Pi or spare phone as a seeder wants it covering every circle they're in, and minting + pasting N invites by hand is busywork. Discussed 2026-05-19; resolved to make seeder setup a single top-level action.
Choice: Add a "global mint" — one action produces a bundle of seed invites for every encrypted circle the user is in, consumed by the launcher in a single paste. **A bundle is just newline-joined `/circle/seed` URLs** — no new invite grammar, no wire-protocol change; each line independently round-trips through the existing `parseSeedInvite`. New additive IPCs: `circle:invite:seed:all` (iterates `circles:joined:` rows, mints via the existing `buildSeedInvite` for every circle carrying an `encryptionKey`, returns `{ bundle, invites, skipped }`; legacy unencrypted circles are skipped since they can't host a blind seeder) and `seeders:listAll` (all seeders across all circles, grouped by seeder pubkey so the UI renders one row per device). The per-circle Broadcast icon + per-circle `SeederManageView` are removed; a single top-level Settings → Seeders section replaces them ("Set up a seeder device" mints the bundle, copy-text + Share, no QR since a multi-circle bundle is too dense; the admitted-seeder list groups by device with a "revoke everywhere" action). The launcher enroll endpoint splits a multi-line bundle and loops the unchanged single-invite `seeder:enroll`. Admission and revocation stay per-circle at the protocol level — each circle's members still independently approve (Q7), `circle:seeder:revoke` is still per-circle, "revoke everywhere" is a UI loop. Reverts the per-circle green-toggle work (commit 67b2661).
Alternatives considered: (a) A single `/circle/seed-bundle?...` URL cramming N circles' params — needs a new parser, hits URL-length limits, and doesn't round-trip the existing `parseSeedInvite`. Rejected; newline-joined existing invites is dead simple. (b) `seeder:enroll` accepting an array `{ invites: [] }` — would move bundle handling into the worklet. Rejected; the launcher host splits + loops the unchanged single-invite primitive, keeping the worklet's parse + rollback logic (slice 3c) untouched. (c) Keep the per-circle Broadcast icon as a supplement alongside the global section — two surfaces for the same feature; the user chose a single option. (d) A deselect checklist before minting — chosen against; one button mints for all encrypted circles, no picker. (e) Per-circle revoke granularity preserved in UI — kept at the protocol level but the UI offers "revoke everywhere" as the primary action since a seeder operator manages a device, not a circle.
Consequences: Touches `src/bare.js` (two new IPC handlers; reverts the `seederCount` field from `snapshotCircle`), `src/ui/App.jsx` (new `SeedersSection` + top-level Collapsible; removes the per-circle Broadcast icon, `onManageSeeders` threading, the per-circle seeders sheet, the old `SeederManageView`, and the `iconBtnStyle` `active` param), `seeder-launcher/host/routes.js` (`/api/enroll` splits a multi-line bundle + aggregates), `seeder-launcher/ui/src/App.jsx` (Enroll accepts a bundle paste, shows aggregated results). New tests in `tests/invite.test.js` covering the bundle format contract (newline-joined invites each round-trip `parseSeedInvite`, blank lines drop on split, single-invite is a one-line bundle, no line carries `enc=`). Proposal amendment appended to `proposals/2026-05-19-blind-seeder-peers.md`. Trust note: a bundle grants the seeder the swarm topics for all its circles at once — broader than per-circle opt-in, acceptable for own-hardware use, and admission stays per-circle so members remain the gate. Build + install validation on D1 / D2 / iPhone + a launcher .pkg rebuild follow.
Follow-on correction (same date): field-testing surfaced a slice-3d revocation bug — the peer-filter's `conn.destroy()` permanently bricked re-admission (a revoked seeder's re-announce can't cross a destroyed connection, so the proposal's "re-admit by writing a fresh row" was impossible) and collateral-killed other circles sharing the connection. Fixed: `src/lib/seederPeerFilter.js` `isConnectionFromRevokedSeeder` (boolean) replaced by `classifySeederConnection` (`admitted` / `revoked-everywhere` / `none`); `onSwarmConnection` skips `corestore.replicate` for a `revoked-everywhere` seeder but never destroys the connection, so the admission channel stays open and re-admission works. The admission dedup was corrected so a *revoked* `seeder:` row no longer suppresses the `seeder:announced` re-admission prompt. A seeder revoked in one circle but admitted in another keeps replicating (blind — ciphertext only); full enforcement applies once it is revoked everywhere. `tests/seederPeerFilter.test.js` rewritten for the classifier.

## 2026-05-19 — desktop launcher for the blind-seeder worklet: Node-host wrapper, macOS first
Tier: T1
Context: The blind-seeder proposal (2026-05-19) lands a `bare.js --seed` worklet that replicates encrypted Autobase blocks for circles without holding the encryption key. The proposal explicitly defers seeder operating-mode UX to a follow-up — `init({ mode: 'seed' })` exists, but no desktop process drives it. Without a one-click install + monitoring story, only the dev team will ever run a seeder, and the proposal's reliability win never reaches real users. Three packaging options surveyed: (a) single Electron app, (b) native Node-host wrappers + localhost browser UI (per OS), (c) Pear-runtime wrapper. Two platform-first options: (a) macOS first, (b) Linux first, (c) all three together. Two branch-base options: (a) stack on the held blind-seeder PRs, (b) build against master.
Choice: Native Node-host wrappers, macOS first, stacked on the held PRs. Layout: a Node SEA single binary spawns `bare src/bare.js --seed` as a subprocess, bridges JSON-newline IPC over stdin/stdout (same envelope BareKit uses on mobile), binds `127.0.0.1:8730`, serves a preact UI via REST + WebSocket. macOS `.pkg` writes the daemon to `/usr/local/lib/pearcircle-seeder/` and templates a LaunchAgent at `~/Library/LaunchAgents/com.pearcircle.seeder.plist` so it auto-starts at login + survives logout. Data directory `~/Library/Application Support/PearCircle Seeder/` holds the worklet's Hyperbee store, a 32-byte random `auth.token` for the localhost API, and a rotating log. Linux + Windows installers follow once the Mac shape is validated. A one-time `src/bare.js` change abstracts the IPC duplex (`BareKit` undefined → `bare-process` stdio) so the same bundle works in both mobile and standalone CLI mode.
Alternatives considered: (a) Single Electron app — ~150MB binary, ARM Linux wobbly, Chromium update cadence becomes our problem, fights the daemon shape; rejected. (b) Pear-runtime wrapper — ideologically aligned but pearcal-native is stalled on a `.bundle` extension-handler blocker in their Phase 2 (see `pearcal-native/docs/superpowers/plans/2026-04-27-pear-desktop.md` §2.4); inheriting that debugging cost is unjustified for a follow-up effort; rejected. (c) Linux-first (.deb + AppImage) — better Pi alignment but slower to validate the e2e smoke since the dev hardware is the Mac mini; deferred to v0.1. (d) All-three-platforms-at-once — premature; ship the simplest shape that demos real replication, then expand. (e) Built against master only — `seeder:enroll` would surface `not-yet-implemented` and the e2e smoke (D1 → seeder → D2 async replication) would be impossible until slices 3c + 3d merge; rejected. (f) Tray icon for daemon discoverability — power users open the browser; deferred. (g) Worklet emits `seeder:connected` / `seeder:disconnected` / `seeder:bytes` events so the launcher renders live state without polling — proposal calls for it but no held PR implements it; the launcher polls `seeder:status` every 5s instead and the events get backfilled in pearcircle proper as a separate follow-up.
Consequences: New `seeder-launcher/` directory at the repo root: Node host (`host/index.js`, `host/worklet.js`, `host/server.js`, `host/routes.js`, `host/auth.js`, `host/dataDir.js`), preact UI (`ui/`), build scripts (`scripts/build-host-sea.sh`, `scripts/build-pkg-macos.sh`, `scripts/postinstall-macos.sh`), LaunchAgent template (`installer/macos/`), README. One small edit to `src/bare.js` introducing the IPC duplex abstraction (4 lines added, 2 lines changed); all 293 existing tests stay green. Phase 1 standalone smoke script verifies identity-persists-across-boots under the bare CLI. Phase 2 dev round-trip (`node host/index.js --dev`) end-to-end works on Linux against the held-PR stack. Phases 3-4 (notarized `.pkg` + e2e D1 → seeder → D2 async smoke) need to land on the Mac mini after slices 1, 3b, 3c, 3d, 4 merge to master. Wiki resync per Constitution §7 follows once Phase 4 passes.

## 2026-05-19 — blind-seeder peers: always-on encrypted-block forwarders with admission protocol
Tier: T3
Context: Pure P2P sync requires both peers to be online simultaneously (or relayed through other live members). For PearCircle this means lastSeen / transition updates from a backgrounded phone often don't reach a member who's not co-online — the structural gap that server-mediated apps like Life360 close by routing through always-on infrastructure. Discussed in conversation 2026-05-18 and 2026-05-19; proposal drafted at `proposals/2026-05-19-blind-seeder-peers.md`. Five-part design: (1) Hypercore block-encryption per circle so a forwarder can replicate ciphertext without ever decrypting it; (2) a separate `/circle/seed` invite shape that withholds the encryption key from seeders; (3) a `seeder:{pubkey}` replicated record carrying the admission state; (4) a Protomux admission channel so the seeder announces itself on first connection and the member emits a `seeder:announced` IPC event for the shell to surface an approval prompt; (5) a peer-filter that drops connections to revoked seeders. All eight open questions resolved 2026-05-19 in the proposal (Q1 always-on encryption with no toggle, Q2 one identity per device, Q3 mode fixed at process launch, Q4 per-circle list only, Q5 `v: 1` on seeder rows, Q6 document anonymity concern only, Q7 any-member admission with transparency, Q8 ship TTL retention knob in v1).
Choice: Land the proposal as six implementation slices (1 encryption infra, 2 seed-mode worklet, 3a wire shapes, 3b member IPCs, 3c seeder replication, 3d admission protocol + peer-filter, 4 Settings UI, 5 retention sweep, 6 this paperwork). The load-bearing privacy decision is **the encryption key is NOT derived from `circleKey`** — it's a separate 32-byte random value generated at circle creation, persisted in the local `circles:joined:{circleId}` row, and carried in member invites via a new `enc=<hex>` query field. Seeders hold `circleKey` (the swarm topic seed; needed to join the swarm) but not `enc`, so they can find peers and replicate encrypted blocks but cannot decrypt content. If we derived `enc` from `circleKey` via any deterministic function, seeders could re-derive it and the privacy boundary would collapse. The split keys are the boundary. A second design deviation from the proposal text: the `seeder:` row schema gains an explicit `writer: hex64` field (signer of this row) so re-admits and revokes by different members each carry their own signature without overloading `addedBy`. LWW on a single `updatedAt` field rather than the proposal's split `addedAt` / `revokedAt` scheme — simpler, matches `presence:` ordering. Q1 (always-on encryption) chosen over the proposal's "default on, build-flag gated" recommendation — stronger and simpler: drops the toggle UI and the unencrypted-new-circle code path entirely; old peers can't join encrypted new circles, so fleet must upgrade before the feature ships to production. Q8 (TTL retention knob in v1) chosen over "defer to follow-up" — the seeder-local `pruneOlderThan` config gives Pi operators an immediate disk-budget tool; pure-helper + per-block sidecar (`seeder:blockTime:{circleId}:{paddedSeq}` rows + `core.on('download')` hook) make it work without the encryption key. The "pruneOlderThan" semantics drift slightly: with no key the seeder cannot read content timestamps, so the cutoff applies to `time-since-this-seeder-received-the-block` rather than `time-since-the-member-wrote-it`. Close enough for disk-budgeting on a Pi.
Alternatives considered: (a) Full extra peer (always-on member, not blind) — simpler to ship but no privacy story; the operator can read all circle content. Rejected per proposal §Background. (b) Tiny push-relay service that wakes sleeping iPhones — best UX but furthest from serverless purity; deferred as a separate follow-up proposal. (c) `addedBy` as both first-admitter and signer (proposal text) — overloads the field, makes revoke-by-someone-other-than-original-admitter awkward. Rejected per slice 3a implementation. (d) Derive `enc = blake2b(circleKey + "enc-v1")` — would simplify invite grammar but defeats the seeder/member key split. Rejected per slice 1 implementation. (e) Default-on encryption with a creation-time checkbox (proposal Q1 recommendation) — extra UI surface and an unencrypted-new-circle code path that almost no real user would hit. Chosen "always-on, no toggle" instead. (f) Defer the TTL retention sweep to a follow-up (proposal Q8 recommendation) — would leave Pi operators with no way to bound disk growth. Chosen "ship the knob in v1" instead. (g) Persisted pending-approvals queue for `seeder:announced` events that the user misses or dismisses — adds complexity; deferred. A dismissed announce will re-surface on the seeder's next swarm reconnect, which is good-enough for v1.
Consequences: Seven implementation PRs (#35–#42) plus this DECISIONS row and the slice 6 wiki-resync. New modules: `src/seeder.js` (seed-mode IPC handlers + identity), `src/seederAdmission.js` (Protomux admission channel), `src/lib/seederApply.js` (apply branch decision + admission/revoke builders), `src/lib/seederPeerFilter.js` (revocation peer-filter), `src/lib/seederRetention.js` (TTL sweep helpers). Touches `src/bare.js` extensively for seed-mode init, the apply branch, member-side IPCs, and the seeder connection handler. UI work in `src/ui/App.jsx`: `SeederManageView` per-circle screen + `SeederApprovalBanner` mounted at app root. ~80 new tests across `tests/seederMode.test.js`, `tests/seederApply.test.js`, `tests/seederPeerFilter.test.js`, `tests/seederRetention.test.js`. Mixed-fleet behavior: encrypted circles are unreachable to old-code peers; the implementation gates encryption creation behind a build flag until the minimum-shipped version is bumped. The seeder runtime itself is reached via `init({ mode: 'seed' })` from the launcher; no launcher ships yet (the desktop-installer follow-up tracked in `TODO.md` covers it). Known limitation: the v1 seeder only replicates the bootstrap writer core, not additional writer cores added via `addWriter`. Multi-writer circles will need slice 3d's admission channel extended to push the additional writer-core keys to the seeder — tracked as a follow-up. Wiki resync per Constitution §7 follows. Each slice PR includes its own build + install validation on D1 + D2 + paired iPhone.

## 2026-05-17 — `lastSeen` value gains optional `stale: boolean` for cold-boot honesty
Tier: T2
Context: PR #20 (`coldboot:selfLastSeen:preloaded`) pre-loads `_selfLastSeen` on worklet init so the existing 15s heartbeat publishes a fresh ts within seconds of opening the app — without waiting on the first GPS fix, which on iOS in SLC-only mode or after a long pause can be 30s+ away. The heartbeat carries a fresh ts but a potentially-hours-old lat/lon. Peers gating "Live" on `ts` alone (`LiveOrAge` in `src/ui/App.jsx`) render the cold-boot peer as currently-at-stale-position, which looks like a teleport once the organic update lands. PR #21 papers over the self-view side with a "Syncing with peers..." pill, but the peer-side misrepresentation remained. Proposal `proposals/2026-05-17-lastseen-stale-flag.md` proposed an additive boolean field so peers can render the truth.
Choice: Add optional `stale: boolean` to the signed `lastSeen:{pubkey}` value. Worklet sets `_selfPositionIsStale = true` in the cold-boot preload pass, includes `stale: true` on heartbeat writes while the flag is set, and clears the flag on the first organic `location:update` for the process. UI's `LiveOrAge` becomes three-way via a new pure helper `src/lib/liveStatus.js`: green-dot "Live" (fresh ts, no flag), amber-dot "Reconnecting" (fresh ts, `stale === true`), or fallback "updated X ago" (stale ts). Apply branch unchanged — value flows through `view.put` as-is. `v` stays at 1; additive amendment per the established §3 rule.
Alternatives considered: (a) Bump `v` to 2 and make the field required — overkill for additive evolution and would force old peers to refuse. (b) Track staleness in the UI by comparing position to last-known and a freshness heuristic — too fragile across reboots, would mis-classify legitimate "I drove home and parked" cases. (c) Don't pre-load `_selfLastSeen` at all — the cold-boot Live gap returns, which was the original user complaint. (d) Suppress the self pin's "Reconnecting" render — considered but rejected; the user knowing their own pin is stale is informative ("why is it at home? oh, GPS is warming up"). Q5 in the proposal (whether to remove the PR #21 pill once this lands) left as a follow-up — both surfaces serve different sides of the gap.
Consequences: Touches `src/bare.js` (1 new module-scope flag, 3 assignment sites, 1 conditional spread in heartbeat payload), `src/lib/liveStatus.js` (new pure helper), `src/ui/App.jsx` (3-way `LiveOrAge`, 2 call sites pass `stale`), `tests/liveStatus.test.js` (9 cases covering all branches plus boundary + defensive parsing). Mixed-fleet behavior: old peers ignore the field per the additive-field rule from proposal `2026-05-03` §3; they continue rendering cold-boot heartbeats as "Live" (lie continues for them, no break). New peers see the truth. Wiki resync per Constitution §7 follows. Wire-protocol proposal `2026-05-03` Amendments section updated. PR #23 = implementation; PR #22 = proposal.

## 2026-05-08 — react to default-network changes by calling `swarm.flush()`
Tier: T1 (no wire change), recorded for the architectural choice and the bugs hit along the way.
Context: 2026-05-07 cold-start investigation showed true cold-start is ~5s but the user's "60s of foreground app-use to resurrect" observation was specifically the wifi → cell → wifi case. Root cause: the foreground location service keeps the JS process alive across swipe-from-recents (working as designed for battery and quick resume), so when the network identity changes the worklet, Hyperswarm and its DHT announcement all carry over. The DHT entry now points peers at an IP this device no longer holds; existing TCP/UTP sockets are dead until keepalive eventually times them out. Hyperswarm has its own internal periodic re-announce, which seems to be what eventually rescued the original observation around the minute mark.
Choice: Listen for default-network changes natively and force a re-announce. Android: `ConnectivityManager.registerDefaultNetworkCallback` in `PearCircleLocationModule`, 2s debounce on the burst Android emits during a transition, emit `PearCircleLocation:network:changed {transport, netHandle}` to the shell, which forwards to the worklet as a `network:changed` IPC. Worklet handler calls `_swarm.flush()` (extracted to `src/lib/networkChange.js` for testability). The first `onAvailable` after registration is skipped via a `hasSeenInitialNetwork` flag; subsequent onAvailable transitions emit. The callback is registered always-on at module init (not gated on the foreground service) — re-announcing on a not-actively-sharing peer is harmless. iOS equivalent (`NWPathMonitor`) deferred to the iOS LocationModule slice.
Alternatives considered: (a) per-topic `swarm.leave(topic)` + `swarm.join(topic, ...)` sweep instead of `flush()` — proposal Open Question #1 left this as a fallback; smoke-test resolved that `flush()` alone is sufficient (D2 saw D1 reappear within 1.2s of detecting disconnect, fresh DHT lookup found the new announcement). The leave/rejoin sweep is unnecessary code. (b) Periodic timer-based re-announce in the worklet (no native callback) — would re-announce constantly to no purpose, or run too rarely to fix the wifi→cell case. Native event-driven is the right shape. (c) Force-stop the app on every network change so cold-start handles it — degrades user experience and contradicts the foreground-service design that PearCircleLocationService relies on. (d) Tie the callback to the foreground service lifecycle — pointless coupling; network state is cheap to track regardless of sharing toggle.
Consequences: Touches `android/app/src/main/java/com/pearcircle/PearCircleLocationModule.kt` (new callback + emit), `app/index.tsx` (one extra `addListener` in `ensureLocationListener`), `src/bare.js` (new IPC handler + `mark('network:changed')` for cold-start observability), `src/lib/networkChange.js` (helper), `tests/networkChange.test.js` (5 cases). Two debug-iteration scars worth flagging for future Kotlin-side work: (1) `init {}` runs before delegated `by lazy` properties are wired up, so accessing one from `init` NPEs — switched to a non-lazy nullable field initialized inside the function; (2) "have we seen the initial network yet" cannot be derived from `lastNetHandle == null` because `onLost` clears it, so a separate `hasSeenInitialNetwork` flag is required. Native diagnostic `Log.w` lines kept in for now (volume is low: ~5 lines per real network transition) until cell-failover stays stable across more sessions. Wiki sync deferred (Constitution §7 covers T2/T3 cross-app patterns; this is single-platform native and probably worth a wiki page once iOS lands and the pattern generalizes).

## 2026-05-07 — circle delete (owner) + circle leave (member); proposal approved
Tier: T3
Context: TODO.md flagged delete/leave as the next governance-gated slice. The wire-protocol proposal §3 already had `removed:{pubkey}` for owner-kicked members but no semantics for owner-tear-down or voluntary departure. Two flows worth addressing together: (a) owner permanently deletes their own circle (cascading tombstone, no rejoin), (b) any member voluntarily leaves a circle (peer-side cleanup of their replicated rows). Drafted as `proposals/2026-05-07-delete-leave-circle.md` with five open questions; resolved per the recommendations on green-light.
Choice: Owner tear-down extends `circle:` row with optional `deleted: boolean, deletedAt: number` (mirrors `place:` soft-delete from DECISIONS 2026-05-05; same LWW-via-linearization-order rule, no new apply branch). Self-leave introduces a new `left:{pubkey}` keyspace, signed by the leaver with self-write apply rule. Filter rule: hide member if `left.leftAt > member.joinedAt` (rejoin is a fresh `member:` write whose `joinedAt` is newer). Five open questions resolved: (1) owner-leave allowed for symmetry but UI nudges owners toward delete; (2) `circle:delete` waits ~2s for replication-ack with a non-blocking "may take a moment" toast; (3) leaver-row filtering applied worklet-side in snapshot helpers, not UI render path; (4) Hyperbee log compaction deferred to the future retention sweep slice; (5) degenerate "owner deletes before any peer ever syncs" case flagged as a follow-up - same root cause as the cold-start delay TODO. Stale-invite enforcement: `circle:join` checks `circle.deleted` after initial sync and refuses with a clear message.
Alternatives considered: (a) New `circleDeleted` tombstone record kind for owner tear-down - explicit but adds an apply branch and a "what if tombstone arrives before circle" edge case; the single-row tombstone in §1 needs zero new apply machinery. (b) Reuse `removed:{pubkey}` for self-leave by relaxing its apply rule - conflates owner-kick (no-rejoin) with voluntary-leave (rejoinable) on one keyspace; cleaner to keep them distinct. (c) Truly local-only self-leave with no on-wire signal - leaver's `member:`/`lastSeen:` rows would persist forever on peers' views, appearing as a stuck stale member. Worse UX. (d) Per-record `del` op on Autobase to hard-delete the leaver's rows - same complexity argument the place-delete decision made (DECISIONS 2026-05-05): hard delete loses the LWW signal and a late-replicating rejoin couldn't beat the absence of a row. The filter-rule approach preserves total ordering through `joinedAt`/`leftAt`.
Consequences: Implementation slice covers `src/bare.js` (new `circle:delete` / `circle:leave` / `circle:cleanup-deleted` IPCs, apply-branch additions for `circle.deleted` event emission and `left:{pubkey}` writes, snapshot helpers learn the leaver-filter rule, `circle:join` post-sync deleted check), `app/index.tsx` (forwards `circle:deleted` and `circle:left` events), `src/ui/App.jsx` (Circles section in Settings sheet with two-tap confirm, peer-side notification + cleanup trigger, JoinView's stale-invite error path). Tests extend `tests/circle.test.js` and `tests/sign.test.js`. v1 remains the floor - only the two test devices have shipped, and both are reinstallable. REVIEW will land at `reviews/2026-05-07-delete-leave-circle.md` after the slice ships. Wiki resync per Constitution §7 once landed.

## 2026-05-05 — `member:{pubkey}.avatar` widens to data URL with dual cap (static 42KB / animated 500KB)
Tier: T3
Context: The wire-protocol proposal §3 typed `member:{pubkey}.avatar` as `base64jpeg` capped at ~30KB encoded (42_000 base64 chars), and the upload pipeline always center-cropped the picked image to 96×96 and JPEG-encoded it via `<canvas>.toDataURL`. That flattens animated GIFs and animated WebP to a single frame on the way in, so an "animated avatar" never landed on disk. Field testing today confirmed this. Three options: (a) accept it as a limitation, keep avatars JPEG-only; (b) widen the schema to a full data URL of any mime, plus a much bigger budget for animated formats so we don't have to compress (which would lose animation); (c) split the field into separate `staticAvatar`/`animatedAvatar` payloads.
Choice: Option (b). The avatar field becomes a full data URL like `data:image/jpeg;base64,...` or `data:image/gif;base64,...`. Two budgets apply, mirroring PearGuard's `MAX_ANIMATED_BASE64` pattern: static formats (JPEG/PNG) keep the existing ~42KB base64 cap, downscaled to 96×96 by canvas; animated formats (`image/gif`, `image/webp`) stored as-is up to ~500KB base64. Bare validates against the larger ceiling so either format passes; the UI applies per-format strictness so static avatars stay cheap to replicate. Renderer (`avatarSrc` helper) accepts both the new data-URL shape and legacy raw-base64 strings (treated as JPEG), so already-saved v1 avatars keep rendering. v1 remains the floor — no peers have shipped beyond the two test devices, so this is an in-flight amendment.
Alternatives considered: (a) JPEG-only — leaves an obviously useful feature on the table; PearGuard already supports animated avatars, so consistency and the user's expectation argue for parity. (c) Split fields — would need two replication paths and a renderer that picks between them, doubles the schema footprint, and conflicts with the simpler "one avatar string per member" mental model. Single-field with mime-prefix is what PearGuard ships; we follow.
Consequences: Updates required to `src/bare.js` (`AVATAR_MAX_BASE64` raised to 500_000; `profile:set` extracts the base64 portion before checking length so the data-URL prefix doesn't eat into the budget; accepts both data URLs and legacy raw base64) and `src/ui/App.jsx` (new `avatarSrc` helper used by Avatar component, ProfileView preview, and the marker pin's `renderBubble`; `onPickFile` does mime-aware routing — animated formats raw-or-reject up to 500KB, static formats raw if small or canvas-compress otherwise). Replication overhead: a 500KB animated avatar is ~12× the previous static cap, but that's still cheap relative to circles' ongoing lastSeen/transition writes; if it ever becomes a problem, future slice can move avatars to Hyperdrive (DECISIONS 2026-05-03 already flagged that as a v2 path). REVIEW filed at `reviews/2026-05-05-avatar-format-amendment.md`. Wiki resync per Constitution §7 once landed.

## 2026-05-05 — reverse-geocoding "near X" via public Nominatim
Tier: T1 (no wire change), but worth recording for the privacy posture shift it introduces.
Context: Member rows in the bottom sheet showed `updated Xs ago` when there was no recent Place transition to anchor the row to a known location. The TODO §Maps UX entry called for a "near X" fallback (street/locality) for that case. Three options for the geocoding source: (a) public Nominatim (OpenStreetMap), (b) self-hosted Nominatim, (c) skip the feature.
Choice: Option (a). Public Nominatim at `https://nominatim.openstreetmap.org/reverse` queried directly from the WebView, results cached in-memory by lat/lon rounded to 4 decimals (~11m grid), per-member hysteresis at 100m so GPS jitter doesn't flip the label between adjacent suburbs/streets, throttled to ~1 request per 1.1 seconds globally per the Nominatim usage policy.
Alternatives considered: (b) Self-hosted Nominatim — eliminates the third-party server but adds significant ops burden (Nominatim is a heavy service to run) for a feature that's nice-to-have. Defer until we self-host other infra. (c) Skip — leaves member rows showing only timestamps for non-Place locations, losing the "where are they roughly" affordance that was the original motivation.
Privacy implication: each unique 4-decimal-place coordinate becomes a query to `nominatim.openstreetmap.org` once per session. That host learns the rough position of any member visible in the sheet. Trade-off summary: smaller leak than the existing tile-host (which already learns the user's viewport area), and only triggered when the user opens the sheet (not constantly in the background). Not stored or logged beyond the in-memory cache that lives for the process lifetime. Documented in the helper's comment block in `src/ui/App.jsx`. Future onboarding hint slice should mention this; future settings slice could add a toggle.
Consequences: New `useReverseGeocodeForMember` hook in `src/ui/App.jsx`, MemberRow extracted from inline `data.members.map` so hook ordering is stable per row. No bare worklet changes — all UI-side. No DECISIONS-level wire impact.

## 2026-05-05 — `place:{id}` gets soft-delete via optional `deleted`/`deletedAt` fields
Tier: T3
Context: Users need to delete places once created — TODO.md called it out as the next governance-gated slice after the place edit feature shipped. The wire-protocol proposal §2 schema for `place:{id}` had no delete semantics; §4 noted the apply rule was last-write-wins on `createdAt` and the "Place delete" TODO line specifically flagged it as needing a proposal amendment for del/tombstone semantics. Field testing on the two test devices was done in the same session as the schema change so any apply-branch regression would surface immediately.
Choice: Soft-delete by adding optional `deleted: boolean` and `deletedAt: number` fields to the existing `place:{id}` value. A delete is a fresh write to the same key with `deleted: true` and `createdAt = Date.now()`. The existing LWW-on-`createdAt` apply rule (proposal §4) keeps the delete winning over older replicas without a new key kind, a new apply branch, or a `del` op type. Renderers, `place:list`, the `circle:get` snapshot, and the in-process geofence tracker all filter rows where `deleted: true`. Undelete is just a non-deleted write with a newer `createdAt`. Old rows without the fields are treated as `deleted: false` (additive, mid-flight v1 amendment). v1 remains the floor — no peers have shipped beyond the test devices.
Alternatives considered: (a) Separate `placeDeleted:{id}` tombstone key — works but introduces a new key kind that every place reader has to consult, doubles the apply-branch work, and adds a "what if the tombstone arrives before the place" edge case. The single-key tombstone in (chosen) needs zero apply changes. (b) `del` op type with a tombstone in the underlying Hyperbee — requires changing every place-reader to scan for tombstones AND adds machinery the proposal explicitly avoided ("Pruned by client after a configurable retention window … NOT a replicated `del` op", §3). Same complexity argument for places. (c) Hard delete via `view.del(key)` — Autobase's apply view supports it, but a hard delete loses the LWW signal: a late-replicating undelete write could resurrect the place because the absence of a row is indistinguishable from "haven't seen the create yet". Soft-delete preserves total ordering through `createdAt`.
Consequences: Updates `src/bare.js` (new `place:delete` IPC, helper `untrackPlace`, helper `isDeleted`, filtering in `place:list` / `circle:get` snapshot / init sweep / apply branch's `place:*` arm) and `src/ui/App.jsx` (Delete button per writable place row, two-tap confirm with 4s auto-disarm, error surface, edit-form auto-close on delete of the place currently being edited). Records pile up forever in the underlying Autobase log; a future retention sweep can prune `deleted: true && deletedAt < now - 30d` if storage becomes a concern. Field-tested cross-device on 2026-05-05 — D1 deletes propagate to D2 within ~3s and the cyan geofence circle vanishes alongside the row. REVIEW filed at `reviews/2026-05-05-place-delete-amendment.md`. Wiki resync per Constitution §7 once landed.

## 2026-05-04 — transition key gains `:{placeId}` suffix to prevent same-tick collisions
Tier: T3
Context: The wire-protocol proposal §3 keyed transitions as `transition:{ts}:{pubkey}`. In the geofence slice we discovered field-observed cases where one FusedLocationProvider result produced two transitions in the same `location:update` tick — typically an exit from one place coincident with an enter to a just-created place — and both used the same `Date.now()` stamp. Both `appendTransition` calls wrote the same Hyperbee key, the second `view.put` overwrote the first in the apply branch, and one transition was silently lost. User reported a stale "left Park" surfacing while a fresh "arrived at ABC Store" never showed; the most plausible reading is a same-tick overwrite (the alternative readings — wide radius, drive-through, stale debug-button data — don't fit the recorded coords).
Choice: Extend the transition key to `transition:{ts}:{pubkey}:{placeId}`. ts-prefix preserves time-ordered reverse scans (used by `circle:get` to surface the latest transitions). pubkey-then-placeId keeps related rows clustered for any future per-member or per-place sweeps. Apply branch parses three colon-separated segments and validates each against the value's `pubkey` and `placeId` fields. v1 remains the floor — no peers had shipped beyond the two test devices, so this is an in-flight amendment, not a v1→v2 transition.
Alternatives considered: (a) Bump per-fire timestamps so concurrent transitions get unique ts values (e.g. T, T+1, T+2) — works without a schema change but creates fictional timestamps that misrepresent when each transition happened, breaks the proposal's "monotonic UTC ms" semantics, and only papers over the underlying ambiguity. (b) Switch the transition row to a list-valued `transition:{ts}:{pubkey}` instead of a scalar, then aggregate per-place inside the value — extra encoding work, awkward to reason about in the apply branch, and the conflict-resolution rule for two writers' concurrent appends becomes its own design problem. (c) Introduce a `del` op type and force the apply branch to detect collisions and merge — way too much machinery for a key-shape problem.
Consequences: Updates `src/bare.js` `appendTransition` to write the new key, and the apply-branch `transition:*` parser to consume three segments. Stale old-format rows on the existing test devices remain in the autobase log and view but never collide with new writes — they age out as fresh transitions land with strictly higher ts (or sit harmlessly until the 30-day retention sweep prunes them, future slice). Resolves the bug from the field test on 2026-05-04. REVIEW filed at `reviews/2026-05-04-transition-key-amendment.md`. Wiki resync per Constitution §7 once landed.

## 2026-05-04 — invite link gains `bootstrap` field for Autobase discovery
Tier: T3
Context: The per-circle Autobase requires joiners to call `new Autobase(store, bootstrapKey, ...)` with the public key of the Autobase's bootstrap writer core. The original `proposals/2026-05-03-wire-protocol.md` §2 invite link did not carry this key. Without it the joiner could not open the Autobase view and replication could not start. Three options surfaced: (a) add a `bootstrap` field to the invite, (b) reuse the device identity keypair as the Autobase writer keypair so `bootstrap == owner.identity.pubkey` and joiners derive it from the existing `inviter` field, (c) exchange the bootstrap key in a per-connection swarm handshake before opening the Autobase.
Choice: Option (a). Invite link grammar in §2 of the wire-protocol proposal now carries a required `bootstrap=<hex(32)>` field. v1 remains the floor since no peers have shipped — this is an in-flight amendment to v1, not a v1→v2 transition. The proposal file is amended in place with an "Amendments" line at the top.
Alternatives considered: (b) Identity-key reuse — works for the initial pair when inviter = owner, but the any-member-can-invite DECISION (2026-05-03) means inviter ≠ owner in the general case, so joiners would still need a separate path to learn the owner's pubkey. Also conflates two distinct cryptographic roles (identity attestation vs Hypercore block signing) on one keypair, a smell we deliberately want to avoid. (c) Per-connection swarm handshake — works but adds a framing layer over the duplex stream with timeouts and edge cases (peer never sends hello, peer disconnects mid-hello). The invite is already the one-shot artifact carrying everything needed to join; one extra field there is the lowest-complexity solution.
Consequences: Updates required to `src/invite.js` (build/parse the new field with 64-char hex validation), `src/bare.js` (`circle:create` generates the per-circle Autobase writer core via `corestore.namespace(circleId)` and surfaces its key as the bootstrap; `circle:join` persists the parsed bootstrap on the local `circles:joined:{id}` row). `tests/invite.test.js` and `tests/circle.test.js` updated to include the field. Resolves the bootstrap-discovery gap and unblocks the per-circle Autobase + replication + addWriter slice. REVIEW filed at `reviews/2026-05-04-invite-bootstrap-amendment.md`. Wiki resynced per Constitution §7.

## 2026-05-03 — avatars stored inline as base64 in `member:{pubkey}` records, ~30KB cap
Tier: T2
Context: Open question #6 in the wire-protocol proposal asked how to replicate per-member profile photos across a circle. Three options surfaced: (a) inline base64 inside `member:{pubkey}`, (b) Hyperdrive per circle with content-addressed hashes, (c) no avatars in v1, initials-only.
Choice: Option (a). Avatars are JPEG, max ~96x96, downscaled and compressed client-side to a ~30KB byte budget (~40KB after base64 inflation). The encoded string lives on the `member:{pubkey}` record as `avatar?: string`. Updating an avatar appends a fresh `member` record to the writer's core and Autobase apply replaces the local row.
Alternatives considered: (a) Hyperdrive per circle — full-resolution and dedupes via content addressing, but adds another P2P primitive per circle, another swarm topic, and another sync surface that can lag the Autobase. Premature for v1 with no other binary-blob use case. Migrate when v2 introduces place photos or voice notes. (b) Initials-only with auto-color pin markers — fastest to ship, no encode/decode work, but real users come from Life360 expecting faces in the roster, and shipping without that is a noticeable downgrade.
Consequences: Resolves open question #6 in `proposals/2026-05-03-wire-protocol.md`. Client must implement a downscale-and-JPEG-compress step before write (sharp on bare? a native module? a JS-only path through the canvas in the WebView is simplest and works on both platforms). 96x96 JPEG at quality ~80 typically lands well under 30KB. Append-only growth from avatar updates is rounding error on a 5-8 person circle. Final go-no-go on the encode path during implementation; the wire field stays optional so a missing or oversized avatar is silently dropped.

## 2026-05-03 — any current member can invite; only owner can remove
Tier: T2
Context: Open question #5 in the wire-protocol proposal asked who in a circle can add new writers. PearCal restricts writer-adds to the owner. Family-sharing apps (Life360, Find My) universally let any member invite. Two pressures collide: tight control (owner-only) vs the lived UX expectation that any family member can pull in a new family member without waking the owner.
Choice: Any current member can issue invite links and append `addWriter` for the resulting key. Only the original circle owner (the `ownerKey` on the `circle` record) can append `removed:{pubkey}` tombstones. The Autobase apply branch for `member` accepts appends from any current writer; the `removed` branch accepts only from `ownerKey`. New members join with full read access to all circle state immediately on writer-add.
Alternatives considered: (a) Owner-only invites (PearCal pattern) — too restrictive for the family use case people are coming from; common UX of "Mom is at work, Dad needs to add the new au pair right now" is blocked. (b) Per-circle `inviteMode` field with owner toggle — added wire surface and a settings UI almost no one will touch in v1. Add additively in v2 if real-world signal demands it.
Consequences: Resolves open question #5 in `proposals/2026-05-03-wire-protocol.md`. Mitigations for the kid-invites-friend risk are social, not protocol: (i) any new member is immediately visible to all circle members, so a bad add is socially detectable in minutes, (ii) the owner can kick at any time. Documented in onboarding for circles where the owner is a parent of younger users.

## 2026-05-03 — per-member mute via separate `presence:{pubkey}` row in v1
Tier: T2
Context: Open question #4 in the wire-protocol proposal asked whether members could temporarily hide their location from the circle, and if so, how to wire it. A family-sharing app without a mute capability is socially uncomfortable; people want occasional privacy from their own circle (doctor visits, dates, surprise planning). Three wire options surfaced: (a) flag on `lastSeen`, (b) separate `presence:{pubkey}` row, (c) silent stop with no wire signal.
Choice: Option (b). New replicated keyspace `presence:{pubkey}` → `{ pubkey, state: 'visible' | 'muted', setAt: number, expiresAt?: number, v: 1 }`. While muted: (i) the writer stops appending new `lastSeen` records, (ii) the writer also stops appending new `transition:` records, (iii) renderers show "Sarah is muted (since 2:14pm)" with no map pin (no stale-location reveal), (iv) `expiresAt` enables client-side auto-unmute ("mute me until 5pm"). Mute is forward-only privacy; previously-replicated data stays replicated. A retroactive history-redaction feature is deliberately out of v1 scope.
Alternatives considered: (a) flag on `lastSeen` — overloads one row with two concerns and blocks future presence states like 'driving' or 'do not disturb' without another schema bump. (b) Silent stop with no signal — indistinguishable from "phone died" or "no signal," produces worry instead of clarity, defeats the social purpose. (c) Hide while muted but keep last pin visible as stale — invites circle members to interpret the pin as current ("she must still be at Home"), defeating the privacy intent.
Consequences: One additional Autobase apply branch (`presence`). One additional UI surface (mute toggle with optional duration picker). Renderer logic: check `presence:{pubkey}` first; if `muted` and `expiresAt > now` (or absent), render the muted state instead of the location. Resolves open question #4 in `proposals/2026-05-03-wire-protocol.md`. Future v2 can add states like `driving` or `do_not_disturb` without a version bump.

## 2026-05-03 — `lastSeen` ships with both `battery` and `isMoving` in v1
Tier: T2
Context: Open question #3 in the wire-protocol proposal asked whether `battery` and `isMoving` ship in v1's `lastSeen` records. Battery is free to read on both platforms (`UIDevice.batteryLevel`, `BatteryManager.getCapacity()`) with no permission. `isMoving` requires `CMMotionActivityManager` on iOS (needs `NSMotionUsageDescription` + runtime prompt) and `ActivityRecognitionClient` on Android (needs `ACTIVITY_RECOGNITION` runtime permission). Both fields enable distinct UX wins: battery distinguishes "phone died" from "muted me," `isMoving` enables "X is on the way" and lets the writer throttle update cadence while stationary.
Choice: Ship both in v1. Add `NSMotionUsageDescription` to `app.json` infoPlist and `ACTIVITY_RECOGNITION` to the Android permissions array. Onboarding includes the motion-permission ask after the location ask. Activity recognition output is smoothed (require N consistent samples before flipping `isMoving`) to filter false positives like phones in clothes dryers.
Alternatives considered: (a) battery only, defer `isMoving` to v2 — saves an onboarding prompt but locks the schema in a way that delays a useful UX. (b) Derive `isMoving` from haversine speed over consecutive `lastSeen` updates — free, no permission, but lower fidelity and only works while the app is actively writing updates. (c) Ship neither, keep schema minimal — gives up real value for a marginal schema-size win.
Consequences: Two extra runtime permission prompts on first launch (location, motion). Onboarding copy must justify both. Resolves open question #3 in `proposals/2026-05-03-wire-protocol.md`. Both fields stay declared optional so a misbehaving writer that omits them still produces valid records.

## 2026-05-03 — `transition:` records retained 30 days, fixed in v1
Tier: T2
Context: The wire-protocol proposal left the retention window for `transition:{ts}:{pubkey}` records open. Realistic volume is 5-20 transitions per member per day at ~100 bytes each, so a 5-member circle at 30 days is ~300KB of replicated state. Storage and sync bandwidth are not binding. The binding constraint is how far back a typical user would actually scroll: a week covers behavioral questions ("did the kids go to school all week"), a month covers monthly ones ("did Dad make it to the dentist").
Choice: 30-day retention, applied as a local sweep on every client (no replicated `del` op). Not user-configurable in v1. A future `transitionRetentionDays` field on the `circle` record can be added additively without a version bump.
Alternatives considered: (a) 7 days — tighter privacy posture, but underwhelms the "how was your week" UX. (b) 90 days — overshoots without a real use case and grows the keyspace. (c) Forever — guaranteed bloat over years. (d) User-configurable in v1 — premature; ship the default, learn from real usage, then add the knob.
Consequences: Resolves open question #2 in `proposals/2026-05-03-wire-protocol.md`. Local sweep job needs implementing (cheap; one Hyperbee range scan per circle per day). Privacy story: anyone with an unlocked phone in the circle sees up to 30 days of place transitions; documented in onboarding.

## 2026-05-03 — tile host is the Protomaps hosted API for v1
Tier: T2
Context: The 2026-05-03 maps decision left tile hosting open. The realistic options are (a) the OSM Foundation's standard tile server, which prohibits production-app use under their Tile Usage Policy and will block heavy traffic, (b) the Protomaps hosted API at `api.protomaps.com`, free for non-commercial use up to a 1M tile-request soft cap per month, or (c) self-hosted Protomaps PMTiles on Cloudflare R2 (zero limits, ~$0.12/month for a US extract on R2's free egress).
Choice: Use the Protomaps hosted API for v1. Sign up for a free API key, set CORS to the app's deep-link host, ship attribution `© OpenStreetMap` in the map UI. PearCircle is non-commercial (no paid app, no ads, no subscription) so the free tier applies as written. The MapLibre tile-source URL will be remotely configurable so a swap to self-hosted PMTiles later is config-only and does not require an app-store release.
Alternatives considered: (a) OSM standard tile server — disallowed by their usage policy, will get blocked at any non-trivial scale. (b) Self-hosted PMTiles from day one — adds R2 setup, a quarterly tile-refresh job, and CDN configuration before we have any users. Premature. (c) MapTiler / Stadia — paid above a small free tier, reintroduces a credit-card dependency we are trying to avoid.
Consequences: One free Protomaps API key per build flavor (debug, release) committed to source. CORS whitelist must include any web preview hosts. If usage approaches the 1M soft cap (rough breakeven ~5,000 daily-active map openers), migrate to self-hosted PMTiles on Cloudflare R2 by swapping the tile URL via the remote config path. The proposal's open question #1 (tile host) is now resolved; updating `proposals/2026-05-03-wire-protocol.md` accordingly.

## 2026-05-03 — identity loss is unrecoverable; rejoin with a new invite
Tier: T2
Context: PearCal invests significant code in mnemonic backup, iCloud Keychain / Android BlockStore round-trips, and personal-base recovery so that a wiped device can rejoin its existing groups with full history. PearCircle's data is intrinsically ephemeral — current location, recent transitions, optional trip log. Past location data has near-zero retention value beyond a short window, and the app's social model already assumes the circle owner can re-issue an invite trivially.
Choice: No mnemonic, no platform-keychain backup, no fork-a-base recovery. A wiped device generates a fresh keypair, the user receives a new invite from any existing circle member, and that fresh key is added as a writer. Old key remains in `members:` until pruned.
Alternatives considered: (a) full PearCal-style identity backup — large surface area for marginal benefit on this data shape. (b) cloud-encrypted backup of the keypair — reintroduces the centralization we are trying to escape. (c) device-pairing to migrate identity across phones — possible follow-up but not v1.
Consequences: Smaller security surface. No `keet-identity-key`, no `bip39-mnemonic`, no SecureStore mnemonic key. Lost-phone story is "ask a circle member to re-invite you." Documented prominently in onboarding and README.

## 2026-05-03 — maps via MapLibre Native + OpenStreetMap tiles
Tier: T2
Context: Need a maps SDK that runs on both Android and iOS, costs nothing per-tile-load, requires no API key, and does not phone home with user location to a centralized service. Google Maps requires a billing account and tracks. Apple MapKit is iOS-only and would force a separate Android maps stack.
Choice: MapLibre Native via `@maplibre/maplibre-react-native` rendered inside the existing WebView UI layer, using OpenStreetMap data via vector tiles. Tile host resolved separately: see the 2026-05-03 Protomaps hosted API decision above.
Alternatives considered: (a) Apple MapKit + Google Maps — two SDKs, two privacy surfaces, ongoing cost. (b) Leaflet inside the WebView — works but lower fidelity, awkward gesture handling on mobile. (c) Mapbox — paid above a low free tier, telemetry-by-default.
Consequences: Tile host must be chosen and an attribution UI element added before public release (OSM license requires it). Offline tile caching is a future enhancement, not v1. Geocoding (place search) requires a separate provider — Nominatim works for low volume.

## 2026-05-03 — geofencing via OS APIs, not in-app polling
Tier: T2
Context: Continuous high-accuracy GPS polling drains battery and is the primary reason location apps get uninstalled. iOS and Android both expose region-monitoring APIs that wake the app on enter/exit transitions without continuous polling — CoreLocation `CLCircularRegion` on iOS (up to 20 regions per app), `GeofencingClient` on Android (up to 100 per app per device).
Choice: Each Place is registered with the OS as a circular region keyed by `{circleId}:{placeId}`. Native modules (`PearCircleLocation`) receive enter/exit callbacks even when the app is killed, then wake the Bare worklet to append a `transitions:` record and broadcast over Hyperswarm. Continuous tracking is opt-in per circle and uses iOS significant-change-location plus Android's lowest-priority location request.
Alternatives considered: (a) JS-side haversine polling at fixed interval — battery-hostile, fails when app is killed. (b) Background fetch every N minutes — lower fidelity, unreliable on iOS. (c) Hybrid (OS geofence + JS polling on top) — adds complexity without clear win.
Consequences: 20-region cap on iOS is the binding constraint. If a user has more than 20 Places across all their circles, we either prioritize closest-N or rotate registration as the user moves. Documented in the wire-protocol proposal.
