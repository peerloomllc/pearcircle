Per-app decision log for PearCircle. Append-only, newest on top. See `/home/tim/peerloomllc/CONSTITUTION.md` §4 for the entry format.

## 2026-06-11 - join follow-ups: tolerate trailing-slash invites, don't leave a shared topic on join rollback
Tier: T1 (more lenient parsing + local in-memory rollback fix; no wire / replicated-record / schema change)
Context: Two issues surfaced while device-validating the circleId-binding guard (DECISIONS 2026-06-11 circleId binding, PR #96). (1) App share links emit `https://peerloomllc.com/circle/join/?circle=...` (trailing slash before the query), but `parseInvite`/`parseSeedInvite` only accepted `/join?` - so a pasted real link gave "Invalid invite". The deep-link path happened to normalize it; the paste-into-Join-UI path did not. (2) `circle:join`'s rollback (deleted-circle branch and the new circleId-mismatch branch) unconditionally did `_topicToCircle.delete` + `_swarm.leave(topic)`. When rejecting a join for a circle the device is already in (a franken invite shares the real circle's circleKey, hence its swarm topic), that left the topic and dropped the mapping the legit membership needs, disconnecting it until restart - confirmed on the TCL during testing.
Choice: (1) `stripPathTrailingSlash` collapses `<basepath>/?` to `<basepath>?` at the top of both parse functions (all four join/seed, https/pear paths). (2) `rollbackJoinTopic(circleId, circleKey)` only leaves the topic + drops the mapping when `_topicToCircle.get(topicHex) === circleId` - i.e. only when this join owns the topic; if it's mapped to another circle (joinCircleTopic no-op'd because we were already on it), it leaves the legit membership untouched. Both rollback branches now call it.
Alternatives: (1) Fix only the deep-link normalizer - rejected, the parse layer is the right place since pasted links bypass deep-link handling. (2) Scan `circles:joined` for a circle sharing the circleKey - rejected, the in-memory `_topicToCircle` owner check is sufficient and synchronous (joinCircleTopic already refuses to overwrite an existing topic mapping).
Consequences: Pasted app-generated links now join. A rejected franken join no longer disconnects a circle you're already in. New tests: trailing-slash cases in `tests/invite.test.js`. The rollback fix is in-memory only and was device-exercised (the franken reject path). Follow-up to PR #96; no proposal (T1).

## 2026-06-11 - bind the seeder-admission channel id to the bootstrap, not the arbitrary circleId
Tier: T2 (one protomux channel-id derivation change with graceful degradation; a join-time guard; no replicated-record / invite-grammar / encryption / local-schema change)
Context: `circleId` is 32 random bytes chosen at creation, carried verbatim in invites, and used as the protomux id for three per-circle channels (seeder-admission, pair, live) plus the seeder enrollment key - but nothing binds it to the circle's cryptographic identity (bootstrap/circleKey) and nothing validates an invite's circleId against the circle it points to. Field-confirmed (the "New"/"Test" test circles, 2026-06-11): the seeder enrolled "New" (bootstrap 34f47458) under "Test"'s circleId 6qCcXe2k, so the seeder's admission channel (id = b4a.from(circleId)) cross-paired with the Pixel's real "Test" channel; New's real members (circleId KeBQFa0i) never paired, silently breaking lastknown + slice-3d writerCores for New. The blind seeder can never read the canonical `circle.id` (no enc key), so it cannot validate circleId itself.
Choice: Two complementary fixes, split by who can validate. (1) Member side, no wire change: `circle:join` now reads the founder-written `circle.id` and REJECTS the join if it disagrees with the invite's circleId ("malformed or stale invite"), so every member's circleId always equals the canonical one - which makes the pair and live channels (member-to-member, keyed by circleId) collision-proof without changing their wire ids. Reject not reconcile, since reconciling means re-keying all local state. (2) Seeder side, wire change: the seeder-admission channel id derives from `blake2b("pearcircle/seeder-admission" || bootstrap)` instead of `b4a.from(circleId)`, in both roles (`admissionChannelId` in seederAdmission.js; member gets bootstrap via base.key, seed via the enrolled row threaded onto the `_seederCircles` entry); protocol bumped `/1` -> `/2`. Even a franken seed invite is then harmless to pairing - the channel keys off the real bootstrap. Proposal `proposals/2026-06-11-circleid-channel-binding.md`.
Alternatives: (a) Re-key `seeder:enrolled:` rows by bootstrap too - deferred as optional hardening; it only addresses a milder residual (a franken circleId squatting a legit circle's enrollment slot), which Fix 1 prevents at the source, and it ripples into the leave/remount paths. (b) Change all three channel ids to bootstrap-derived - unnecessary once Fix 1 makes member-to-member collisions impossible; one wire change beats three. (c) Make circleId = f(bootstrap) so it's self-validating - cleaner in theory but breaks existing random-circleId circles and rewrites invite/state keying everywhere.
Consequences: Old member <-> new seeder won't share the admission channel until both update (announce/lastknown/writerCores pause for that pair); topic-based bootstrap-core replication is unchanged, so basic seeding keeps working - graceful, no data loss. Acceptable for the small controlled fleet (forced upgrade). New unit tests `tests/admissionChannelId.test.js`. The pair and live channels keep keying by circleId (protected by Fix 1). REVIEWS skipped per Constitution §6 (single-author, scoped). Follow-up: enrollment-by-bootstrap hardening if a franken seed invite ever reaches a seeder in practice.

## 2026-06-10 - blind seeder slice 3d: replicate every member's writer core, not just the founder's
Tier: T2 (one additive Protomux message on the existing seeder-admission channel; no replicated-record kind, invite-grammar, or encryption change; backward compatible at the wire-v1 floor)
Context: Field investigation of the Hudgins family circle (member "Leah" showed live position updating but place-transition history frozen ~1 day) traced to the blind seeder mirroring only the founder's writer core. `tools/seeder-coverage.js` confirmed 1 of 6 member writer cores held (founder 344 blocks; the other five at 0). v1 of the blind-seeder proposal (`src/bare.js` mountSeederCircle comment) only ever guaranteed bootstrap-core replication; on-demand corestore session opening never proactively pulls non-founder writer cores. Result: a member's durable writes (transitions) only propagate when that member and a recipient are online simultaneously - exactly the co-presence gap the seeder was meant to close. Live position kept flowing because it rides the ephemeral broadcast, which has no replication gate.
Choice: Mirror the existing `lastknownCores` admission message one-for-one for writer cores. New `[3] writerCores` message (member -> seed) on `pearcircle/seeder-admission/1` carries `{ cores: [{pubkey, coreKey}] }` (coreKey = a member's Autobase writer-core key; validated + capped at 256 by `normalizeWriterCores`). Member collects writer keys from `base.activeWriters` (`collectCircleWriters`) and pushes on seeder-confirm (`pushWriterCoresToSeeder`) and on the 5s sweep when the set changes (`repushWriterCoresToSeeders`, sig-deduped) - the sweep is also the newly-added-writer trigger. Seeder opens each core blind via `openPeerCore` (no enc key, ciphertext only) and `download({start:0,end:-1})`s the full history (`handleSeederWriterCores` / `openSeederWriterCore`), tracked in `_seederCircles[].writerCores`, persisted as `seeder:writerCore:{circleId}:{coreKey}` and re-opened on boot. Proposal: `proposals/2026-05-19-blind-seeder-peers.md` amendment 2026-06-10.
Alternatives: (a) Have the seeder enumerate writers itself from the autobase system core - impossible, it's blind (no enc key). (b) Per-core TTL retention now - deferred; the sweep's block-time sidecar is keyed per-circle-seq and clears only the bootstrap, so writer cores download full history and are NOT TTL-pruned in this slice (full history is the desired backstop default anyway; per-core retention is a clean follow-up). (c) Recreate circles - unnecessary; writer keys are stable, existing circles backfill once members run this build and reconnect.
Consequences: Additive and backward compatible - old members omit the message, old seeders ignore it; rollback is clean (remove the message + handler, fall back to bootstrap-only). No persisted-state migration. New unit tests `tests/seederWriterCores.test.js` (normalizeWriterCores validation + cap). Verify: re-run `tools/seeder-coverage.js` against the Hudgins invite and confirm 1/6 -> 6/6; manual smoke of the frozen-transition repro (a backgrounded member's transition reaches a second device with the first offline, via the seeder). Inspection tools `tools/seeder-opcount.js` + `tools/seeder-coverage.js` left in tree. REVIEWS skipped per Constitution §6 (single-author, additive).

## 2026-06-03 - LocationManager fallback when Google Play Services is absent
Tier: T1 (Android-native only, no wire/IPC/Hyperbee/permission change)
Context: A new user on LineageOS without microG reported the app cannot find them while Organic Maps can. Both Android location surfaces (the foreground service stream and `requestSingleFix`) use Google's FusedLocationProvider, which silently delivers nothing on a ROM without Play Services and without microG -- the GMS client classes are bundled in the APK so nothing throws, the provider just never produces a fix. Geofencing is unaffected (computed in the worklet from `location:update`, no `GeofencingClient` on Android).
Choice: Hybrid detection. A shared `gmsAvailable(Context)` (via `GoogleApiAvailability.isGooglePlayServicesAvailable == SUCCESS`) gates the fused path; when GMS is absent both surfaces fall back to the platform `LocationManager`. GPS_PROVIDER is primary, NETWORK_PROVIDER only when GPS is absent (no fusion/blending). Streaming keeps the fused 10s/10m cadence; one-shot uses `getCurrentLocation` on API 30+ and freshest last-known on API 29. Both feed the existing `emitToJs` -> `location:update` path unchanged. Proposal `proposals/2026-06-03-android-location-no-gms.md`.
Alternatives: always use LocationManager (rejected -- regresses battery/accuracy for the ~99% with GMS); require microG (rejected -- conflicts with the decentralization principle and surprises de-Googled users who are the natural audience).
Consequences: Fused path unchanged and regression-checked on a GMS device (D2: fused selected, FGS up, no crash). The fallback path itself is NOT yet validated on a GMS-less device -- needs the reporter's LineageOS device or an AOSP/google_apis-free emulator with a mock route before merge. Single-commit revert restores fused-only.

## 2026-06-01 - shed dead swarm sockets via a secret-stream timeout (not UDX's)
Tier: T1 (local connection lifecycle, no wire/persisted change)
Context: The 2026-05-30 lag investigation pinned the "location lag while moving" limitation on a dead Hyperswarm socket lingering in the connection set until UDX's slow internal timeout, blocking the redial that would replicate the fresh position. The earlier `discovery.refresh()` fix couldn't beat the dead socket sitting in the set. HyperDHT already sends a 5s keepalive but no secret-stream `timeout` was set.
Choice: Arm `conn.setTimeout(15s)` on every member connection (refreshed by the 5s keepalives on a live link, trips fast on a dead one so Hyperswarm redials) plus a one-shot `sendKeepAlive()` nudge on foreground and each `location:update`. Behind a `STALE_CONN_PROBE_ENABLED` kill-switch. Proposal `proposals/2026-06-01-stale-connection-shedding.md`.
Alternatives: discovery.refresh() (tried, didn't help); cellular-handoff network:changed (follow-up); leave as-is (rejected, the lag was a real complaint).
Consequences: On-device validated 2026-05-31 (drop at 15s, prompt redial, no lag while moving), but no controlled flag-on/off A/B was completed -- adoption rests on positive signals + no regression. The persistent events.log built to measure it crashed the worklet (per-mark IPC flood) and was reverted; revisit only with batched flushing. The cold-boot first-write gate (~66s) is a separate unaddressed bug. Updates the TODO "moving lag" entry.

## 2026-05-29 - push wake-on-demand deferred (decision B): no PeerLoom-operated wake relay
Tier: T3 (deferred, no code shipped)
Context: The 2026-05-29 "stale location" investigation explored remote-waking a suspended iPhone via push so it grabs a fresh fix on demand - the one freshness gap not closed by the blind seeder (last-known while offline), the Tier 1 CLVisit + self-region wakes (PR #64), and the foreground one-shot (PR #63). Full design drafted at `proposals/2026-05-29-push-wake-on-demand.md`.
Choice: Do not build push. Rely on seeder + Tier 1 + foreground one-shot. The load-bearing reason is a credential constraint, not the protocol design (which holds up): iOS push requires authenticating to APNs with PearCircle's own team-scoped credential (a `.p8` token key or a per-app push certificate, both tied to the PeerLoom Apple account G79ALD29NA), which cannot be handed to self-hosters because whoever holds it can push to every user, and Apple offers no per-user or per-circle variant. iOS has no other remote-wake-from-suspended mechanism. So any wake relay is necessarily PeerLoom-operated, which conflicts with the decentralization principle ("no PeerLoom-operated central infra") and matches the blind-seeder stance ("PeerLoom does not operate seeders"). The gap push would close is also narrow: a stationary, suspended phone's position is still correct, only the timestamp looks old, and liveness is already conveyed separately by the swarm-connected dot (2026-05-17 swarm-live-signal).
Alternatives considered: (a) Build a zero-knowledge PeerLoom-operated relay (opaque token in, content-free silent push out, no location / identity / circle data, no logs) - the least objectionable possible central service, acceptable as a narrow exception; rejected for now to preserve the no-central-infra principle and because the marginal freshness gain over seeder + Tier 1 is thin. (b) Distribute the APNs `.p8` to self-hosters - non-viable, it can push to all users. (c) Per-deployment bundle IDs or PushKit/VoIP - defeats one shipped app and/or violates Apple policy. (d) Android high-priority FCM - same Google-held-credential shape, same conclusion.
Consequences: No code. `proposals/2026-05-29-push-wake-on-demand.md` kept as a DEFERRED design reference (apply rules, relay protocol, verify plan, zero-knowledge mitigation); a gitignored TODO.md item under "Future / not v1" tracks revival. If revisited, the zero-knowledge relay is the starting point and would be T3 (new `push:{pubkey}` record, `aps-environment` entitlement + `remote-notification` background mode, the relay service). Silent-push caveats (best-effort, throttled, dropped in Low Power Mode, cannot relaunch a force-quit app) mean even a future build layers on seeder + Tier 1, never replaces them.

## 2026-05-22 — member removal is rejoin-overridable, not a permanent ban
Tier: T1
Context: Owner-side member removal shipped earlier 2026-05-22 (PR #59) implemented the `removed:{pubkey}` keyspace from the v1 wire protocol (proposal 2026-05-03 §3) as a permanent tombstone — `snapshotCircle` hid the pubkey unconditionally and the apply branches dropped all of a removed member's later writes, matching the proposal's "suppresses future appends from pubkey" wording. Testing surfaced that this makes removal an irreversible dead-end: a kicked member cannot rejoin even with a valid invite link, and an owner who removes someone by mistake has no way back. The owner asked for removal to be reversible by simply rejoining, explicitly accepting that this means a removed member can rejoin repeatedly.
Choice: Make `removed:` behave like the `left:` voluntary-leave tombstone instead of a permanent block. A member is hidden only while `removed.ts` strictly beats their `member:` row `joinedAt` (`memberHiddenByRemoved`, the same rule as `memberHiddenByLeft`); a rejoin writes a fresh `member:` row whose `joinedAt` beats `removed.ts` and brings them straight back. The owner kicking again writes a newer `removed.ts` (LWW on `ts`) that re-hides them. The owner kick still fires `circle:removed-self` so the removed member gets the notice and local teardown, but that emit is now gated on `removed.ts` post-dating the local `circles:joined` joinedAt, so a stale `removed:` row replaying after a rejoin does not bounce the member again. The four apply-branch write-suppression checks (member / lastSeen / presence / transition) are dropped — `removed:` is now purely a snapshot-time filter, exactly like `left:`. No wire-format change: the `removed:` row schema is unchanged and `ts` was already present.
Alternatives considered: (a) Keep removal permanent and add an owner "Allow back" re-admit action that lifts the tombstone (an LWW `removed:` row with a `lifted` flag, plus a "Removed members" UI surface) — more deliberate and owner-controlled, but more code and UI, and the owner explicitly wanted the simpler self-service rejoin. (b) Identity persistence to prevent the reinstall-duplicate at the source — still tracked in TODO as the longer-term prevention, orthogonal to this. (c) Keep the apply-branch suppression so a removed member's writes never land — dropped for consistency with `left:` (which has no suppression) and because a removed member's app tears the circle down on `circle:removed-self` and stops writing anyway; the owner accepted the residual that a removed member who ignores the notice could still briefly write.
Consequences: `src/lib/circleFilter.js` gains `memberHiddenByRemoved`; the `shouldAcceptRemovedRow` doc is corrected (no longer "unconditional"). `src/bare.js`: the `removed:` apply branch goes LWW on `ts` with the local-joinedAt-gated `circle:removed-self` emit, `snapshotCircle` tracks `removedAtByPubkey` (a Map of ts, not a Set) and filters via `memberHiddenByRemoved`, the four suppression checks are removed, and the `seeder:` apply branch's `writerRemoved` now uses `memberHiddenByRemoved` so a rejoined member is not treated as a removed seeder-writer. `src/ui/App.jsx`: the removed-self notice copy mentions rejoining. New `memberHiddenByRemoved` tests in `tests/circleFilter.test.js`. Tradeoff accepted by the owner: removal is no longer a ban — anyone with a join link can rejoin, repeatedly; "remove" is a cleanup / soft-eject, not moderation against a hostile actor. No proposal (T1); the 2026-05-03 wire proposal's "suppresses future appends" wording for `removed:` is superseded by this entry.

## 2026-05-21 - Linux seeder-launcher packaging: AppImage + .deb, x86_64 + arm64
Tier: T1
Context: The seeder-launcher had validated macOS (.pkg + LaunchAgent) and Windows (NSIS + nssm service) packaging; Linux was the documented next step. The 2026-05-19 launcher decision picked macOS first with Linux and Windows to follow once the Mac shape was validated, and the Mac shape is now validated. Linux desktops split between Debian-family distros (apt/dpkg) and everything else, and the canonical always-on seeder box is a Raspberry Pi (arm64), so neither a single format nor a single arch was sufficient.
Choice: Ship two formats, each for x86_64 and arm64. A Debian .deb installs the flat payload under /opt/pearcircle-seeder with a /usr/bin/pearcircle-seeder symlink; its postinst installs and enables a systemd user service for the installing user (resolved via $SUDO_USER) and runs loginctl enable-linger so the seeder survives logout and reboot. An AppImage is the portable single-file option for non-Debian distros; --install-service registers the same systemd user unit pointed at the AppImage's own path, a desktop launch (double-click or a Gear Lever-style menu entry, detected as no controlling terminal) auto-installs that service on first run and then opens the token-authed dashboard in the browser, and a bare terminal run starts the host in the foreground for debugging. Both reuse the macOS payload shape unchanged (host-bundled.js + bundled Node + bare runtime + worklet.bundle + addon prebuilds + ui), which is what host/index.js resolvePaths already expects in a non-dev install. The build runs locally on a Linux x86_64 box with no VM or remote machine, unlike macOS (Mac mini) and Windows (QEMU VM); arm64 is cross-packaged from the same x86_64 host and shipped build-verified only.
Alternatives considered: (a) A system-wide systemd service instead of a user service - would run the seeder as root or a dedicated system account with the data dir outside any user home; rejected to keep the data-dir story identical to macOS (per-user $HOME) and because a seeder is a personal always-on process, not machine infrastructure. (b) deb only, or AppImage only - a .deb excludes Fedora/Arch/openSUSE users while an AppImage alone gives Debian/RPi users no apt integration; shipping both costs little once payload staging is shared. (c) An x86_64-only build - excludes the Raspberry Pi, the most likely seeder host. (d) systemctl --global enable for the user unit - enables it for every user on the box; rejected, the .deb should set up only the user who installed it.
Consequences: New scripts under seeder-launcher/scripts/: stage-payload-linux.sh (shared payload staging), build-deb-linux.sh, build-appimage-linux.sh, build-linux.sh (orchestrator). build-host-sea.sh generalized to honor NODE_OS/NODE_ARCH overrides, with macOS default behavior unchanged. New installer assets under seeder-launcher/installer/linux/: the systemd user unit template, AppRun, the .desktop file, deb maintainer-script templates, the install README. The foreign-arch bare runtime is fetched with npm pack because npm install refuses it with EBADPLATFORM; appimagetool and the per-arch AppImage runtimes are downloaded and cached under dist/cache. x86_64 AppImage and .deb are build-and-run validated on the Fedora build box; arm64 packages are build-verified only and need run-testing on real arm64 hardware. seeder-launcher/README.md updated to link the Linux and Windows install guides (it still listed both as "planned" though Windows had already shipped). No proposal (T1); REVIEWS skipped per Constitution §6.

## 2026-05-21 — seeder revocation signal: content-blind "you were revoked" notice
Tier: T2
Context: A blind seeder never learns it was revoked. Revocation writes a revoked `seeder:{pubkey}` row into a circle's autobase and the member-side peer-filter (`classifySeederConnection`) stops replicating to that seeder, but the seeder is blind (it does not open the autobase), the admission channel was one-way (seeder announces, member listens), and the connection is deliberately left open for re-admission so a disconnect cannot be inferred either. Result: the seeder-launcher dashboard kept listing a revoked circle as actively seeded. Proposal `proposals/2026-05-21-seeder-revocation-signal.md`, approved as T2; four open questions resolved in conversation 2026-05-21 before implementation.
Choice: Add a second message to the per-circle seeder-admission Protomux channel — `[1] revoked` (member to seed), alongside the existing `[0] announce` (seed to member). When a member connects to a peer and finds, in a shared circle, that peer's `seeder:{pubkey}` row revoked, it sends `{ type:'revoked', circleId, revokedAt }` on channel open. The seeder records `seeder:revoked:{circleId}` (`{ circleId, revokedAt, noticedAt }`) in its local Hyperbee — a new seeder-local, never-replicated row family. `seeder:enrolled:list` joins enrolled rows with the revoked rows and returns `revoked` + `revokedAt` per circle; the launcher dashboard renders a "revoked" badge and an explanatory line, with the existing Leave action to clear it. Four resolved questions: (Q1 authentication) the notice is advisory and UI-only — a blind seeder has no member list so it cannot verify the sender, enforcement stays member-side, and a spoofed notice at worst shows a dismissable wrong badge; the notice never drives automatic or network behavior. (Q2 topic behavior) a revoked seeder keeps announcing and joining the swarm topic — acting on an unauthenticated notice would let a spoof deny a legitimate seeder and would contradict the keep-the-connection-open peer-filter design. (Q3 lifecycle) a revoked circle stays in the enrolled list with a badge until the user clicks Leave — auto-removal would hide the reason and let a spoof silently evict circles. (Q4 re-admission) the `seeder:revoked` row is cleared by the seeder's existing per-block `download` hook the first time real blocks replicate for that circle again — block replication is unspoofable, so it is evidence-based re-admission and needs no new message type; an in-memory `_seederRevokedCircles` set keeps the per-block path a cheap `has()` check.
Alternatives considered: (a) A cryptographically verifiable notice that forwards the signed revocation row — rejected: the blind seeder has no member list, so even a valid signature only proves "someone signed this", not "an authorized member signed this"; full verification is unreachable and would push the change to T3. (b) Stop announcing / leave the topic on revocation (Q2) — saves a little bandwidth but lets a spoofed notice cause real denial and breaks instant re-admission. (c) Auto-remove a revoked circle from the dashboard (Q3) — hides why a circle vanished and is spoof-exploitable. (d) Clear the revoked row via an "admitted" notice from the member (Q4) — carries the same spoofability as the revoked notice; the block-replication signal cannot be faked. (e) Re-evaluate revocation on every autobase update rather than per connection — out of scope; the existing enforcement is already per-connection-cycle and the proposal's "within one connection cycle" bar matches it.
Consequences: New module `src/lib/seederRevocation.js` (pure helpers: `revocationNoticeFor`, `recordRevocationNotice`, `clearRevocationNotice`, `loadRevokedCircles`). `src/seederAdmission.js` gains the `[1] revoked` message plus `onRevoked` / `revokedNotice` params. `src/bare.js`: `_seederRevokedCircles` in-memory set, `handleSeederRevocationNotice`, the per-block `download` hook clears revocations, the member connection handler captures seeder rows during `classifySeederConnection` and emits notices, the seed init loads the revoked set. `src/seeder.js`: `seeder:enrolled:list` returns `revoked` + `revokedAt`; `seeder:leave` also deletes the `seeder:revoked` row. `seeder-launcher/ui/` renders the badge. New `tests/seederRevocation.test.js` plus revocation cases in `tests/seederMode.test.js`. Compat: purely additive — old peers ignore the unknown Protomux message, so an old seeder or old member just keeps a stale dashboard (status quo, no break); the new local row family reads as "not revoked" when absent, no migration. REVIEWS skipped per Constitution §6 (T2). Wiki resync per §7 follows. Build + install validation on the seeder-launcher .pkg + member devices follows.
Follow-on (same date): device testing surfaced two gaps, both fixed on the same branch. (1) Instant propagation — the base design sent the revoke notice only on admission-channel open (a fresh connection), so revoking while already connected to the seeder did not reach it until the connection cycled. `circle:seeder:revoke` now also pushes the notice over live connections immediately via an in-memory `_memberAdmissionChannels` registry (keyed by connection + circleId; `src/seederAdmission.js` exposes a `sendRevoked` method, `_connPubkey` maps a connection to its seeder pubkey). (2) Durable revocation — `handleSeederAnnounce` auto-re-admitted any announcing seeder including revoked ones, which silently undid every revocation on the seeder's next reconnect (a seeder announces on every connection). This revises the 2026-05-20 follow-on "a revoked row falls through — re-announce is a re-admission request": an announce from an already-revoked seeder now keeps the revocation in force and re-sends the notice instead of re-admitting (which also closes the race where the seeder mounts the circle after the member connected). First-time admission stays a frictionless auto-admit; re-admitting a revoked seeder is now explicit via `circle:seeder:approve`. No wire change — a new send-trigger, an in-memory registry, and an admission-path behavior change. (3) Re-admit UI — device testing then showed the member UI had no re-admit control: it had relied entirely on the now-removed auto-re-admit (the old "re-admit later by setting the seeder up again" flow), and a revoked seeder simply dropped off Settings → Seeders. `src/ui/App.jsx` SeedersSection now keeps revoked seeders listed (live and revoked circles shown separately) and offers a "Re-admit" action that loops `circle:seeder:approve` over the revoked circles; the revoke confirm copy was corrected to match. Mixed-fleet caveat: an old-code member still auto-re-admits, so durable revocation holds once a circle's members are all on new code — acceptable at the v1 floor. The 2026-05-21 proposal carries a matching Amendment section.

## 2026-05-20 — seeder auto-follow: one-time setup, new circles seed automatically
Tier: T2
Context: The global-mint amendment (2026-05-19) made seeder setup one action, but the bundle is a snapshot — create a circle later and the user has to re-mint, re-paste, and re-approve. The user expects seeder setup to be genuinely one-time: designate a seeder device once, and every circle created or joined afterward should seed itself with no further action. Raised 2026-05-20 after testing the global mint with a freshly-created circle.
Choice: Add an auto-follow relationship. The member marks a seeder device as "followed" via an explicit per-seeder toggle in Settings → Seeders, default off (chosen over default-on and over an "armed by Set up a seeder device" mode — default-off is the transparent option; a seeder admitted to a shared circle never silently starts following the user's other circles). Followed state is local-only `seederfollow:{pubkey}` Hyperbee rows, never replicated. ## 2026-05-19 — blind-seeder peers: always-on encrypted-block forwarders with admission protocol
Tier: T3
Context: Pure P2P sync requires both peers to be online simultaneously (or relayed through other live members). For PearCircle this means lastSeen / transition updates from a backgrounded phone often don't reach a member who's not co-online — the structural gap that server-mediated apps like Life360 close by routing through always-on infrastructure. Discussed in conversation 2026-05-18 and 2026-05-19; proposal drafted at `proposals/2026-05-19-blind-seeder-peers.md`. Five-part design: (1) Hypercore block-encryption per circle so a forwarder can replicate ciphertext without ever decrypting it; (2) a separate `/circle/seed` invite shape that withholds the encryption key from seeders; (3) a `seeder:{pubkey}` replicated record carrying the admission state; (4) a Protomux admission channel so the seeder announces itself on first connection and the member emits a `seeder:announced` IPC event for the shell to surface an approval prompt; (5) a peer-filter that drops connections to revoked seeders. All eight open questions resolved 2026-05-19 in the proposal (Q1 always-on encryption with no toggle, Q2 one identity per device, Q3 mode fixed at process launch, Q4 per-circle list only, Q5 `v: 1` on seeder rows, Q6 document anonymity concern only, Q7 any-member admission with transparency, Q8 ship TTL retention knob in v1).
Choice: Land the proposal as six implementation slices (1 encryption infra, 2 seed-mode worklet, 3a wire shapes, 3b member IPCs, 3c seeder replication, 3d admission protocol + peer-filter, 4 Settings UI, 5 retention sweep, 6 this paperwork). The load-bearing privacy decision is **the encryption key is NOT derived from `circleKey`** — it's a separate 32-byte random value generated at circle creation, persisted in the local `circles:joined:{circleId}` row, and carried in member invites via a new `enc=<hex>` query field. Seeders hold `circleKey` (the swarm topic seed; needed to join the swarm) but not `enc`, so they can find peers and replicate encrypted blocks but cannot decrypt content. If we derived `enc` from `circleKey` via any deterministic function, seeders could re-derive it and the privacy boundary would collapse. The split keys are the boundary. A second design deviation from the proposal text: the `seeder:` row schema gains an explicit `writer: hex64` field (signer of this row) so re-admits and revokes by different members each carry their own signature without overloading `addedBy`. LWW on a single `updatedAt` field rather than the proposal's split `addedAt` / `revokedAt` scheme — simpler, matches `presence:` ordering. Q1 (always-on encryption) chosen over the proposal's "default on, build-flag gated" recommendation — stronger and simpler: drops the toggle UI and the unencrypted-new-circle code path entirely; old peers can't join encrypted new circles, so fleet must upgrade before the feature ships to production. Q8 (TTL retention knob in v1) chosen over "defer to follow-up" — the seeder-local `pruneOlderThan` config gives Pi operators an immediate disk-budget tool; pure-helper + per-block sidecar (`seeder:blockTime:{circleId}:{paddedSeq}` rows + `core.on('download')` hook) make it work without the encryption key. The "pruneOlderThan" semantics drift slightly: with no key the seeder cannot read content timestamps, so the cutoff applies to `time-since-this-seeder-received-the-block` rather than `time-since-the-member-wrote-it`. Close enough for disk-budgeting on a Pi.
Alternatives considered: (a) Full extra peer (always-on member, not blind) — simpler to ship but no privacy story; the operator can read all circle content. Rejected per proposal §Background. (b) Tiny push-relay service that wakes sleeping iPhones — best UX but furthest from serverless purity; deferred as a separate follow-up proposal. (c) `addedBy` as both first-admitter and signer (proposal text) — overloads the field, makes revoke-by-someone-other-than-original-admitter awkward. Rejected per slice 3a implementation. (d) Derive `enc = blake2b(circleKey + "enc-v1")` — would simplify invite grammar but defeats the seeder/member key split. Rejected per slice 1 implementation. (e) Default-on encryption with a creation-time checkbox (proposal Q1 recommendation) — extra UI surface and an unencrypted-new-circle code path that almost no real user would hit. Chosen "always-on, no toggle" instead. (f) Defer the TTL retention sweep to a follow-up (proposal Q8 recommendation) — would leave Pi operators with no way to bound disk growth. Chosen "ship the knob in v1" instead. (g) Persisted pending-approvals queue for `seeder:announced` events that the user misses or dismisses — adds complexity; deferred. A dismissed announce will re-surface on the seeder's next swarm reconnect, which is good-enough for v1.
Consequences: Seven implementation PRs (#35–#42) plus this DECISIONS row and the slice 6 wiki-resync. New modules: `src/seeder.js` (seed-mode IPC handlers + identity), `src/seederAdmission.js` (Protomux admission channel), `src/lib/seederApply.js` (apply branch decision + admission/revoke builders), `src/lib/seederPeerFilter.js` (revocation peer-filter), `src/lib/seederRetention.js` (TTL sweep helpers). Touches `src/bare.js` extensively for seed-mode init, the apply branch, member-side IPCs, and the seeder connection handler. UI work in `src/ui/App.jsx`: `SeederManageView` per-circle screen + `SeederApprovalBanner` mounted at app root. ~80 new tests across `tests/seederMode.test.js`, `tests/seederApply.test.js`, `tests/seederPeerFilter.test.js`, `tests/seederRetention.test.js`. Mixed-fleet behavior: encrypted circles are unreachable to old-code peers; the implementation gates encryption creation behind a build flag until the minimum-shipped version is bumped. The seeder runtime itself is reached via `init({ mode: 'seed' })` from the launcher; no launcher ships yet (the desktop-installer follow-up tracked in `TODO.md` covers it). Known limitation: the v1 seeder only replicates the bootstrap writer core, not additional writer cores added via `addWriter`. Multi-writer circles will need slice 3d's admission channel extended to push the additional writer-core keys to the seeder — tracked as a follow-up. Wiki resync per Constitution §7 follows. Each slice PR includes its own build + install validation on D1 + D2 + paired iPhone.

## 2026-05-08 — react to default-network changes by calling `swarm.flush()`
Tier: T1 (no wire change), recorded for the architectural choice and the bugs hit along the way.
Context: 2026-05-07 cold-start investigation showed true cold-start is ~5s but the user's "60s of foreground app-use to resurrect" observation was specifically the wifi → cell → wifi case. Root cause: the foreground location service keeps the JS process alive across swipe-from-recents (working as designed for battery and quick resume), so when the network identity changes the worklet, Hyperswarm and its DHT announcement all carry over. The DHT entry now points peers at an IP this device no longer holds; existing TCP/UTP sockets are dead until keepalive eventually times them out. Hyperswarm has its own internal periodic re-announce, which seems to be what eventually rescued the original observation around the minute mark.
Choice: Listen for default-network changes natively and force a re-announce. Android: `ConnectivityManager.registerDefaultNetworkCallback` in `PearCircleLocationModule`, 2s debounce on the burst Android emits during a transition, emit `PearCircleLocation:network:changed {transport, netHandle}` to the shell, which forwards to the worklet as a `network:changed` IPC. Worklet handler calls `_swarm.flush()` (extracted to `src/lib/networkChange.js` for testability). The first `onAvailable` after registration is skipped via a `hasSeenInitialNetwork` flag; subsequent onAvailable transitions emit. The callback is registered always-on at module init (not gated on the foreground service) — re-announcing on a not-actively-sharing peer is harmless. iOS equivalent (`NWPathMonitor`) deferred to the iOS LocationModule slice.
Alternatives considered: (a) per-topic `swarm.leave(topic)` + `swarm.join(topic, ...)` sweep instead of `flush()` — proposal Open Question #1 left this as a fallback; smoke-test resolved that `flush()` alone is sufficient (D2 saw D1 reappear within 1.2s of detecting disconnect, fresh DHT lookup found the new announcement). The leave/rejoin sweep is unnecessary code. (b) Periodic timer-based re-announce in the worklet (no native callback) — would re-announce constantly to no purpose, or run too rarely to fix the wifi→cell case. Native event-driven is the right shape. (c) Force-stop the app on every network change so cold-start handles it — degrades user experience and contradicts the foreground-service design that PearCircleLocationService relies on. (d) Tie the callback to the foreground service lifecycle — pointless coupling; network state is cheap to track regardless of sharing toggle.
Consequences: Touches `android/app/src/main/java/com/pearcircle/PearCircleLocationModule.kt` (new callback + emit), `app/index.tsx` (one extra `addListener` in `ensureLocationListener`), `src/bare.js` (new IPC handler + `mark('network:changed')` for cold-start observability), `src/lib/networkChange.js` (helper), `tests/networkChange.test.js` (5 cases). Two debug-iteration scars worth flagging for future Kotlin-side work: (1) `init {}` runs before delegated `by lazy` properties are wired up, so accessing one from `init` NPEs — switched to a non-lazy nullable field initialized inside the function; (2) "have we seen the initial network yet" cannot be derived from `lastNetHandle == null` because `onLost` clears it, so a separate `hasSeenInitialNetwork` flag is required. Native diagnostic `Log.w` lines kept in for now (volume is low: ~5 lines per real network transition) until cell-failover stays stable across more sessions. Wiki sync deferred (Constitution §7 covers T2/T3 cross-app patterns; this is single-platform native and probably worth a wiki page once iOS lands and the pattern generalizes).

## 2026-05-07 — circle delete (owner) + circle leave (member); proposal approved
Tier: T3
Context: TODO.md flagged delete/leave as the next governance-gated slice. The wire-protocol proposal §3 already had `removed:{pubkey}` for owner-kicked members but no semantics for owner-tear-down or voluntary departure. Two flows worth addressing together: (a) owner permanently deletes their own circle (cascading tombstone, no rejoin), (b) any member voluntarily leaves a circle (peer-side cleanup of their replicated rows). (b) Reuse `removed:{pubkey}` for self-leave by relaxing its apply rule - conflates owner-kick (no-rejoin) with voluntary-leave (rejoinable) on one keyspace; cleaner to keep them distinct. (c) Truly local-only self-leave with no on-wire signal - leaver's `member:`/`lastSeen:` rows would persist forever on peers' views, appearing as a stuck stale member. Worse UX. (d) Per-record `del` op on Autobase to hard-delete the leaver's rows - same complexity argument the place-delete decision made (DECISIONS 2026-05-05): hard delete loses the LWW signal and a late-replicating rejoin couldn't beat the absence of a row. The filter-rule approach preserves total ordering through `joinedAt`/`leftAt`.
Consequences: Implementation slice covers `src/bare.js` (new `circle:delete` / `circle:leave` / `circle:cleanup-deleted` IPCs, apply-branch additions for `circle.deleted` event emission and `left:{pubkey}` writes, snapshot helpers learn the leaver-filter rule, `circle:join` post-sync deleted check), `app/index.tsx` (forwards `circle:deleted` and `circle:left` events), `src/ui/App.jsx` (Circles section in Settings sheet with two-tap confirm, peer-side notification + cleanup trigger, JoinView's stale-invite error path). Tests extend `tests/circle.test.js` and `tests/sign.test.js`. v1 remains the floor - only the two test devices have shipped, and both are reinstallable. REVIEW will land at `reviews/2026-05-07-delete-leave-circle.md` after the slice ships. Wiki resync per Constitution §7 once landed.

## 2026-05-05 — `member:{pubkey}.avatar` widens to data URL with dual cap (static 42KB / animated 500KB)
Tier: T3
Context: The wire-protocol proposal §3 typed `member:{pubkey}.avatar` as `base64jpeg` capped at ~30KB encoded (42_000 base64 chars), and the upload pipeline always center-cropped the picked image to 96×96 and JPEG-encoded it via `<canvas>.toDataURL`. That flattens animated GIFs and animated WebP to a single frame on the way in, so an "animated avatar" never landed on disk. Field testing today confirmed this. Three options: (a) accept it as a limitation, keep avatars JPEG-only; (b) widen the schema to a full data URL of any mime, plus a much bigger budget for animated formats so we don't have to compress (which would lose animation); (c) split the field into separate `staticAvatar`/`animatedAvatar` payloads.
Choice: Option (b). The avatar field becomes a full data URL like `data:image/jpeg;base64,...` or `data:image/gif;base64,...`. Two budgets apply, mirroring PearGuard's `MAX_ANIMATED_BASE64` pattern: static formats (JPEG/PNG) keep the existing ~42KB base64 cap, downscaled to 96×96 by canvas; animated formats (`image/gif`, `image/webp`) stored as-is up to ~500KB base64. Bare validates against the larger ceiling so either format passes; the UI applies per-format strictness so static avatars stay cheap to replicate. Renderer (`avatarSrc` helper) accepts both the new data-URL shape and legacy raw-base64 strings (treated as JPEG), so already-saved v1 avatars keep rendering. v1 remains the floor — no peers have shipped beyond the two test devices, so this is an in-flight amendment.
Alternatives considered: (a) JPEG-only — leaves an obviously useful feature on the table; PearGuard already supports animated avatars, so consistency and the user's expectation argue for parity. (c) Split fields — would need two replication paths and a renderer that picks between them, doubles the schema footprint, and conflicts with the simpler "one avatar string per member" mental model. Single-field with mime-prefix is what PearGuard ships; we follow.
Consequences: Updates required to `src/bare.js` (`AVATAR_MAX_BASE64` raised to 500_000; `profile:set` extracts the base64 portion before checking length so the data-URL prefix doesn't eat into the budget; accepts both data URLs and legacy raw base64) and `src/ui/App.jsx` (new `avatarSrc` helper used by Avatar component, ProfileView preview, and the marker pin's `renderBubble`; `onPickFile` does mime-aware routing — animated formats raw-or-reject up to 500KB, static formats raw if small or canvas-compress otherwise). Replication overhead: a 500KB animated avatar is ~12× the previous static cap, but that's still cheap relative to circles' ongoing lastSeen/transition writes; if it ever becomes a problem, future slice can move avatars to Hyperdrive (DECISIONS 2026-05-03 already flagged that as a v2 path). REVIEW filed at `reviews/2026-05-05-avatar-format-amendment.md`. Wiki resync per Constitution §7 once landed.

## 2026-05-05 — `place:{id}` gets soft-delete via optional `deleted`/`deletedAt` fields
Tier: T3
Context: Users need to delete places once created — TODO.md called it out as the next governance-gated slice after the place edit feature shipped. The wire-protocol proposal §2 schema for `place:{id}` had no delete semantics; §4 noted the apply rule was last-write-wins on `createdAt` and the "Place delete" TODO line specifically flagged it as needing a proposal amendment for del/tombstone semantics. Field testing on the two test devices was done in the same session as the schema change so any apply-branch regression would surface immediately.
Choice: Soft-delete by adding optional `deleted: boolean` and `deletedAt: number` fields to the existing `place:{id}` value. A delete is a fresh write to the same key with `deleted: true` and `createdAt = Date.now()`. The existing LWW-on-`createdAt` apply rule (proposal §4) keeps the delete winning over older replicas without a new key kind, a new apply branch, or a `del` op type. Renderers, `place:list`, the `circle:get` snapshot, and the in-process geofence tracker all filter rows where `deleted: true`. Undelete is just a non-deleted write with a newer `createdAt`. Old rows without the fields are treated as `deleted: false` (additive, mid-flight v1 amendment). v1 remains the floor — no peers have shipped beyond the test devices.
Alternatives considered: (a) Separate `placeDeleted:{id}` tombstone key — works but introduces a new key kind that every place reader has to consult, doubles the apply-branch work, and adds a "what if the tombstone arrives before the place" edge case. The single-key tombstone in (chosen) needs zero apply changes. (b) `del` op type with a tombstone in the underlying Hyperbee — requires changing every place-reader to scan for tombstones AND adds machinery the proposal explicitly avoided ("Pruned by client after a configurable retention window … NOT a replicated `del` op", §3). Same complexity argument for places. (c) Hard delete via `view.del(key)` — Autobase's apply view supports it, but a hard delete loses the LWW signal: a late-replicating undelete write could resurrect the place because the absence of a row is indistinguishable from "haven't seen the create yet". Soft-delete preserves total ordering through `createdAt`.
Consequences: Updates `src/bare.js` (new `place:delete` IPC, helper `untrackPlace`, helper `isDeleted`, filtering in `place:list` / `circle:get` snapshot / init sweep / apply branch's `place:*` arm) and `src/ui/App.jsx` (Delete button per writable place row, two-tap confirm with 4s auto-disarm, error surface, edit-form auto-close on delete of the place currently being edited). Records pile up forever in the underlying Autobase log; a future retention sweep can prune `deleted: true && deletedAt < now - 30d` if storage becomes a concern. Field-tested cross-device on 2026-05-05 — D1 deletes propagate to D2 within ~3s and the cyan geofence circle vanishes alongside the row. REVIEW filed at `reviews/2026-05-05-place-delete-amendment.md`. Wiki resync per Constitution §7 once landed.

## 2026-05-04 — transition key gains `:{placeId}` suffix to prevent same-tick collisions
Tier: T3
Context: The wire-protocol proposal §3 keyed transitions as `transition:{ts}:{pubkey}`. In the geofence slice we discovered field-observed cases where one FusedLocationProvider result produced two transitions in the same `location:update` tick — typically an exit from one place coincident with an enter to a just-created place — and both used the same `Date.now()` stamp. Both `appendTransition` calls wrote the same Hyperbee key, the second `view.put` overwrote the first in the apply branch, and one transition was silently lost. User reported a stale "left Park" surfacing while a fresh "arrived at ABC Store" never showed; the most plausible reading is a same-tick overwrite (the alternative readings — wide radius, drive-through, stale debug-button data — don't fit the recorded coords).
Choice: Extend the transition key to `transition:{ts}:{pubkey}:{placeId}`. ts-prefix preserves time-ordered reverse scans (used by `circle:get` to surface the latest transitions). pubkey-then-placeId keeps related rows clustered for any future per-member or per-place sweeps. Apply branch parses three colon-separated segments and validates each against the value's `pubkey` and `placeId` fields. v1 remains the floor — no peers had shipped beyond the two test devices, so this is an in-flight amendment, not a v1→v2 transition.
Alternatives considered: (a) Bump per-fire timestamps so concurrent transitions get unique ts values (e.g. T, T+1, T+2) — works without a schema change but creates fictional timestamps that misrepresent when each transition happened, breaks the proposal's "monotonic UTC ms" semantics, and only papers over the underlying ambiguity. (b) Switch the transition row to a list-valued `transition:{ts}:{pubkey}` instead of a scalar, then aggregate per-place inside the value — extra encoding work, awkward to reason about in the apply branch, and the conflict-resolution rule for two writers' concurrent appends becomes its own design problem. (c) Introduce a `del` op type and force the apply branch to detect collisions and merge — way too much machinery for a key-shape problem.
Consequences: Updates `src/bare.js` `appendTransition` to write the new key, and the apply-branch `transition:*` parser to consume three segments. Stale old-format rows on the existing test devices remain in the autobase log and view but never collide with new writes — they age out as fresh transitions land with strictly higher ts (or sit harmlessly until the 30-day retention sweep prunes them, future slice). Resolves the bug from the field test on 2026-05-04. REVIEW filed at `reviews/2026-05-04-transition-key-amendment.md`. Wiki resync per Constitution §7 once landed.

## 2026-05-03 — any current member can invite; only owner can remove
Tier: T2

## 2026-05-03 — per-member mute via separate `presence:{pubkey}` row in v1
Tier: T2
Context: Open question #4 in the wire-protocol proposal asked whether members could temporarily hide their location from the circle, and if so, how to wire it. A family-sharing app without a mute capability is socially uncomfortable; people want occasional privacy from their own circle (doctor visits, dates, surprise planning). Three wire options surfaced: (a) flag on `lastSeen`, (b) separate `presence:{pubkey}` row, (c) silent stop with no wire signal.
Choice: Option (b). New replicated keyspace `presence:{pubkey}` → `{ pubkey, state: 'visible' | 'muted', setAt: number, expiresAt?: number, v: 1 }`. While muted: (i) the writer stops appending new `lastSeen` records, (ii) the writer also stops appending new `transition:` records, (iii) renderers show "Sarah is muted (since 2:14pm)" with no map pin (no stale-location reveal), (iv) `expiresAt` enables client-side auto-unmute ("mute me until 5pm"). Mute is forward-only privacy; previously-replicated data stays replicated. A retroactive history-redaction feature is deliberately out of v1 scope.
Alternatives considered: (a) flag on `lastSeen` — overloads one row with two concerns and blocks future presence states like 'driving' or 'do not disturb' without another schema bump. (b) Silent stop with no signal — indistinguishable from "phone died" or "no signal," produces worry instead of clarity, defeats the social purpose. (c) Hide while muted but keep last pin visible as stale — invites circle members to interpret the pin as current ("she must still be at Home"), defeating the privacy intent.
Consequences: One additional Autobase apply branch (`presence`). One additional UI surface (mute toggle with optional duration picker). Renderer logic: check `presence:{pubkey}` first; if `muted` and `expiresAt > now` (or absent), render the muted state instead of the location. Resolves open question #4 in `proposals/2026-05-03-wire-protocol.md`. Future v2 can add states like `driving` or `do_not_disturb` without a version bump.

## 2026-05-03 — `lastSeen` ships with both `battery` and `isMoving` in v1
Tier: T2
Context: Open question #3 in the wire-protocol proposal asked whether `battery` and `isMoving` ship in v1's `lastSeen` records. Battery is free to read on both platforms (`UIDevice.batteryLevel`, `BatteryManager.getCapacity()`) with no permission. `isMoving` requires `CMMotionActivityManager` on iOS (needs `NSMotionUsageDescription` + runtime prompt) and `ActivityRecognitionClient` on Android (needs `ACTIVITY_RECOGNITION` runtime permission). ## 2026-05-03 — geofencing via OS APIs, not in-app polling
Tier: T2
Context: Continuous high-accuracy GPS polling drains battery and is the primary reason location apps get uninstalled. iOS and Android both expose region-monitoring APIs that wake the app on enter/exit transitions without continuous polling — CoreLocation `CLCircularRegion` on iOS (up to 20 regions per app), `GeofencingClient` on Android (up to 100 per app per device).
Choice: Each Place is registered with the OS as a circular region keyed by `{circleId}:{placeId}`. Native modules (`PearCircleLocation`) receive enter/exit callbacks even when the app is killed, then wake the Bare worklet to append a `transitions:` record and broadcast over Hyperswarm. Continuous tracking is opt-in per circle and uses iOS significant-change-location plus Android's lowest-priority location request.
Alternatives considered: (a) JS-side haversine polling at fixed interval — battery-hostile, fails when app is killed. (b) Background fetch every N minutes — lower fidelity, unreliable on iOS. (c) Hybrid (OS geofence + JS polling on top) — adds complexity without clear win.
Consequences: 20-region cap on iOS is the binding constraint. If a user has more than 20 Places across all their circles, we either prioritize closest-N or rotate registration as the user moves. Documented in the wire-protocol proposal.
